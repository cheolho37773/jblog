## PR 단위 소유권 판정 규칙 (오케스트레이터 확정, ①의 테스트 기준)

입력: PR의 변경(`git diff --name-status --no-renames <base>...<head>`), 커밋별 변경(같은 범위의 각 커밋), 브랜치 이름, 지시서, `roles.json`, 계약 생성 검사 통과 여부. 파일 이름이 바뀐 경우는 삭제 + 추가로 본다.

| # | 규칙 | 판정 |
|---|---|---|
| R1 작업 ID | 브랜치 `<유형>/<나머지>`에서 `docs/work/*/tasks/*.md` 파일 이름(ID) 중 `<나머지>`와 같거나 `<나머지>`가 `<ID>-`로 시작하는 **가장 긴** ID. 없으면 작업 ID 없음 | — |
| R2 참여 역할 | 지시서의 `- 참여 역할: a, b` 줄(쉼표 구분). 지시서가 있는데 이 줄이 없거나 `roles.json`에 없는 역할이 있으면 **실패**. 작업 ID 없음 → 참여 역할 없음 | — |
| R3 Codex 결과 보호 | `protected` 경로(`*.codex.md`, `docs/plan/feedback/**`)는 **모든 커밋에서 추가(A)만** 허용하고, 경로가 이 작업 ID의 공통 허용(`pr_common_allow`)에 맞아야 한다. 어느 커밋에서든 수정(M)·삭제(D)되면 **실패**. (협업 §5.2의 "해시 기록" 방식 대신 커밋별 이력으로 판정 — 같은 보장, 대응 기록 형식 변경 불필요) | 통과/실패 |
| R4 공통 허용 | 이 작업 ID의 `pr_common_allow` 경로(지시서, `docs/reviews/<ID>/**`, 피드백 파일)와 `shared` 경로(`docs/work/*/tasks/**`) | 통과 |
| R5 잠금 파일 | `pnpm-lock.yaml` 변경은 PR에 `package.json`(루트 또는 `*/package.json`) 변경이 함께 있을 때만 | 통과/실패 |
| R6 계약 생성물 | `frontend/src/generated/**`는 브랜치가 `contract/`로 시작하고 계약 생성 검사(`--contract-check-passed`)가 통과했을 때만. 그 밖에는 **실패**(역할 범위와 무관) | 통과/실패 |
| R7 OpenAPI 계약 | `backend/openapi.json`은 `contract/` 브랜치이고 참여 역할에 backend-dev가 있을 때만. 그 밖에는 **실패** | 통과/실패 |
| R8 오케스트레이터 | 모든 PR에서 허용: `docs/**`(R3 대상 제외), `README.md`, `CLAUDE.md`, `AGENTS.md`, `.claude/**`, `scripts/ownership/roles.json`. 규칙 원본은 `roles.json`의 새 항목 `pr_orchestrator_allow`(③이 추가) | 통과 |
| R9 역할 범위 | 위에 해당하지 않는 경로는 참여 역할 중 하나라도 허용하면 통과(역할별 `allow`/`deny`/`allow_after_deny`는 훅 `check-ownership.py`와 같은 의미). `roles.orchestrator`(`**`)는 R9에 쓰지 않는다(R8로 대체) | 통과/실패 |

- 판정 결과는 위반 목록(경로 + 규칙 번호 + 이유). 하나라도 있으면 종료 코드 1
- 지시서 없는 PR(기획 문서 PR 등)은 R3·R4(작업 ID 없음 → 해당 없음)·R5~R8만 적용 → 문서·오케스트레이터 경로만 바뀌면 통과, 코드가 바뀌면 실패

## 판정 스크립트 인터페이스 (①의 테스트 대상)

`scripts/ownership/pr_ownership_check.py` (③ 구현, 표준 라이브러리만):

| 함수 | 동작 |
|---|---|
| `find_task_id(branch: str, task_ids: Iterable[str]) -> str \| None` | R1 |
| `parse_participating_roles(brief_text: str) -> list[str]` | R2의 줄 파싱(없으면 빈 목록, 앞뒤 공백 제거) |
| `check_pr(*, changes: list[tuple[str, str]], commits: list[list[tuple[str, str]]], branch: str, task_id: str \| None, roles: list[str], brief_found: bool, rules: dict, contract_check_passed: bool) -> list[str]` | R2~R9. `changes`·`commits`의 원소는 `(상태, 경로)`(상태 `A`/`M`/`D`). 위반 메시지 목록(빈 목록 = 통과). 각 메시지는 경로와 규칙 번호(`R3` 등)를 포함 |
| `main(argv: list[str]) -> int` | `--base`, `--head`, `--branch`, `--contract-check-passed`. git으로 입력을 모아 `check_pr` 호출, 위반을 출력하고 0/1 반환 |

## 동작 규약 (③)

| # | 항목 | 규약 |
|---|---|---|
| 1 | 트리거 | `.github/workflows/ci.yml`: 작업 브랜치 `push`(`dev`·`main` 제외) + `dev` 대상 `pull_request`. `pull_request_target` 금지. 같은 브랜치의 이전 실행은 취소(`concurrency`) |
| 2 | 권한 | 워크플로 최상위 `permissions: contents: read`(필요한 잡만 최소로 추가). 외부 액션은 **커밋 SHA로 고정**(태그 아님), 주석에 버전 |
| 3 | 잡 | 이름이 상태 검사 이름이 되므로 안정적으로: `lint`(lint·format:check·typecheck), `test`(루트 `test` — 단위·e2e·규칙 테스트, `python3 -m unittest discover -s scripts/tests`), `integration`(backend `test:integration`, Testcontainers), `e2e`(Playwright Chromium, `--with-deps`), `build`(더미 셸 환경값으로 루트 `build`), `contract`(`pnpm gen:api-types --check` + `openapi:generate` 후 `git diff --exit-code backend/openapi.json`), `docker`(두 Dockerfile 빌드, push 없음), `ownership-check`(R1~R9, `contract` 결과를 `--contract-check-passed`로 전달 — 같은 잡에서 검사를 돌리거나 `needs`로 연결) |
| 4 | 설치 | `.nvmrc`의 Node, corepack(`packageManager` 버전), `pnpm install --frozen-lockfile`. pnpm 저장소 캐시 사용 가능. 캐시 없는 첫 설치에서 Prisma 엔진이 받아지는지 확인(M0-06 인계) |
| 5 | SHA 3종 | 각 실행 요약(`$GITHUB_STEP_SUMMARY`)에 head SHA, base SHA(PR이면 PR base, push면 `origin/dev`와의 merge-base), 검사한 커밋(PR이면 merge commit) |
| 6 | `pnpm verify` | 루트 스크립트: CI의 `lint`·`test`·`build`·`contract`와 같은 명령(통합·E2E·Docker는 시간이 걸리므로 `verify:full`로 분리해도 됨 — 결정 기록) |
| 7 | Dockerfile | 멀티 스테이지, 베이스 이미지는 **정확한 태그**(예: `node:24.x.y-alpine` — 저장소 Node 버전과 맞춤), 비root 실행, `HEALTHCHECK`. backend: `prisma.config.ts`·`src/config/env.source.ts`(빌드 결과)·`prisma/` 포함, 시작 시 `prisma migrate deploy` 후 `node dist/main.js`(백엔드 §8). frontend: Next `standalone` 출력 사용. 빌드 단계에 필요한 환경값은 `ARG`로 받고(공개 값만), 비밀값을 이미지에 넣지 않는다. `.dockerignore`로 `.env*`·`node_modules`·`.git` 제외 |
| 8 | 가독성 | 스크립트는 협업 §10-a(작은 함수, 이름, "왜" 주석), 워크플로는 잡·단계 이름을 한국어 또는 명확한 영어로 |

## CI 확인 방법 (오케스트레이터)

워크플로는 push해야 실제로 돈다. Codex 최종 검수 전에는 작업 브랜치를 push하지 않으므로, **시험용 브랜치 `chore/M0-08-ci-trial`**(같은 작업 ID로 판정됨)에 push해 CI를 확인·수정하고, 끝나면 원격·로컬에서 삭제한다. 거부 시나리오도 `chore/M0-08-ci-reject-*` 시험 브랜치로 확인하고 Merge하지 않고 삭제한다(M0 계획 §5).
