## 테스트 대상 인터페이스 (② 테스트 선작성 기준, 오케스트레이터 확정)

②는 아래 진입점만 쓰고, ③은 이 시그니처를 지킨다. 접속 URL(비밀번호 포함)은 로그·단정 메시지에 넣지 않는다.

| 경로 (소유) | 내보내는 것 | 동작 |
|---|---|---|
| `backend/test/setup-integration-database.ts` (devops, ①) | `readIntegrationDatabaseUrl(): string` | 통합 테스트용 빈 DB URL |
| `backend/test/support/integration-db.ts` (backend-dev, ③) | `prepareIntegrationDatabase(): Promise<IntegrationDatabase>` | 위 URL에 마이그레이션 적용(여러 번 불려도 멱등) 후 `{ databaseUrl, prisma }` 반환. `prisma`는 앱과 같은 생성 클라이언트 |
| 〃 | `resetDatabase(prisma): Promise<void>` | 모든 앱 테이블 데이터 비우기(스키마·확장·인덱스 유지). 각 테스트 파일 `beforeEach`용 |
| 〃 | `runSeed(databaseUrl: string): Promise<void>` | `prisma/seed.ts`와 같은 seed를 그 DB에 실행 |
| 〃 | `createIntegrationEnv(databaseUrl: string): Record<string, unknown>` | `createApp`에 넘길 env(`NODE_ENV=test`, 더미 `API_PORT`, `DATABASE_URL`) |
| 〃 | `closeIntegrationDatabase(db: IntegrationDatabase): Promise<void>` | 연결 해제 |
| `backend/src/bootstrap.ts` (기존) | `createApp(rawEnv, options)` | `DATABASE_URL` 필수 추가 외 계약 동일 |

- 제약 시험은 Prisma 모델 API(`prisma.postSlug.create` 등, 모델·필드명은 §3.2)로 행을 만들고 Prisma의 unique 위반 오류(`P2002`) 또는 DB 오류를 단정한다. 인덱스·확장·테이블 존재는 `prisma.$queryRaw`로 `pg_indexes`·`pg_extension`·`information_schema.tables`를 조회한다
- health 실패 시험은 닫힌 포트를 가리키는 더미 `DATABASE_URL`(예: `127.0.0.1:1`)로 `createApp` — DB 없이 앱이 떠야 한다(규약 7)
- 기존 M0-04 e2e·단위 테스트의 `createApp`·`validateEnv` 호출에는 더미 `DATABASE_URL`을 추가한다(②가 수정)

- 고른 버전

| 패키지 | 버전 |
|---|---|
| @testcontainers/postgresql | 12.2.2 (최신 안정. `testcontainers` 12.2.2를 의존성으로 함께 설치 — 직접 import하지 않아 따로 추가하지 않음) |

- 접속 정보 전달 방식 (process.env를 쓰지 않는 이유)
  - Jest globalSetup의 전역 변수는 테스트 파일에 보이지 않는다. Jest 문서 방식(globalSetup에서 `process.env` 설정)은 설정 모듈 밖 `process.env` 금지 규칙에 걸리고 `test/setup*.ts`는 예외 경로가 아니다. 규칙 예외를 만들지 않고 **파일로 전달**한다
  - globalSetup이 `backend/node_modules/.cache/jblog-integration/database.json`(권한 600)에 URL을 쓰고, globalTeardown이 지운다. `node_modules`라 커밋되지 않고 worktree마다 경로가 달라 섞이지 않는다
  - 비밀번호는 실행마다 `randomBytes`로 새로 만든다(고정 비밀번호를 코드에 두지 않음). 사용자·DB 이름은 Testcontainers 기본값
- ②·③과의 접점
  - **넘겨 주는 것**: `backend/test/setup-integration-database.ts`의 `readIntegrationDatabaseUrl(): string` — 컨테이너의 PostgreSQL 접속 URL(`postgres` 스킴, 사용자·비밀번호·호스트·포트·DB 포함). 통합 테스트 실행 안에서만 동작하고, 밖에서 부르면 실행 방법을 알려 주는 오류를 던진다. 반환값에 비밀번호가 있으므로 로그·단정 메시지에 그대로 출력하지 않는다. `INTEGRATION_POSTGRES_IMAGE`도 export
  - **③ backend-dev(`backend/test/support/`)가 할 일**: 이 URL로 `prisma migrate deploy`(또는 Prisma 프로그램 API) 적용, seed 실행, PrismaClient/`AppEnv`(`DATABASE_URL`) 생성 헬퍼. 컨테이너는 실행 전체에서 1개이고 마이그레이션은 적용되지 않은 빈 DB로 넘겨진다. 여러 int-spec 파일이 각자 헬퍼를 부르면 `migrate deploy`가 반복 실행되므로 멱등이어야 하고(규약 4와 같음), 파일 간 데이터 격리(테이블 비우기·트랜잭션 등)도 헬퍼가 정한다. 파일은 직렬 실행(`maxWorkers: 1`)
  - 주의(③): Prisma CLI(`migrate deploy`)를 자식 프로세스로 부르면 `DATABASE_URL`을 자식 env로 넘겨야 하는데, `env: { ...process.env, DATABASE_URL }`처럼 `test/support/`에서 `process.env`를 읽으면 ESLint 규칙에 걸린다. Prisma 프로그램 API나 `backend/*.config.ts`(예외 경로, 예: `prisma.config.ts`) 쪽에서 해결하는 방법을 먼저 찾고, 규칙 예외가 필요하면 멈추고 보고한다
  - **② test-engineer**: int-spec은 `backend/test/**/*.int-spec.ts`에 둔다. 컨테이너 기동은 globalSetup에서 끝나므로 각 테스트 시간에 포함되지 않는다(테스트 타임아웃 60초)
- 루트 `pnpm test` 포함 여부: **넣지 않음**. Docker가 필요하고 첫 실행 시 이미지 내려받기로 느려서, Docker 없는 환경의 루트 검사를 깨지 않게 한다. CI 연결은 M0-08
- `allowBuilds` 판단(모두 `false`, 동작에 불필요): `ssh2`(선택적 네이티브 암호 바인딩 빌드, 실패해도 exit 0이고 순수 JS로 동작, Docker `ssh://` 접속 전용), `cpu-features`(ssh2의 optionalDependency), `protobufjs`(postinstall이 버전 표기 경고만 출력)

- 보류: drift 검사
  - 이유: 최신 Prisma의 `migrate diff` 플래그(`--from-migrations`는 shadow DB 필요, 설정 파일 방식)와 수동 SQL 인덱스 표현 방식이 ③에서 정해지고, CLI를 자식 프로세스로 부르려면 `DATABASE_URL`을 자식 env로 넘겨야 해 `process.env` 규칙과 부딪힌다(① 알아둘 점과 같음). 테스트로 넣으면 구현 방식을 미리 고정하게 된다
  - ④·오케스트레이터 확인 명령(예시, 플래그는 ③이 기록한 Prisma 버전 기준): 빈 DB에 `migrate deploy` 후 `prisma migrate diff --from-<그 DB> --to-schema prisma/schema.prisma --exit-code` → exit 0, 그리고 `prisma migrate dev`가 새 마이그레이션을 만들지 않음. **수동 SQL 인덱스(trgm·부분 unique)를 스키마가 모르면 diff가 "인덱스 삭제"를 drift로 낸다** — ③이 스키마 표현(예: `@@index(... type: Gin)`, 확장 선언, 부분 인덱스 지원 여부)으로 맞추거나 차이가 나지 않는 방법을 기록해야 한다
- ③ 구현자가 알아야 할 점
  - `prepareIntegrationDatabase()`는 **한 파일 안에서 두 번** 불린다(`schema.int-spec` 재적용 사례). 두 번째 반환값을 `closeIntegrationDatabase`로 닫아도 첫 번째 `prisma`는 계속 쓸 수 있어야 한다
  - `resetDatabase`는 `_prisma_migrations`를 비우면 안 된다(재적용 사례가 이력 행 수를 셈). 확장·인덱스도 유지
  - unique 위반은 `code === 'P2002'` 또는 SQLSTATE `23505`(코드나 메시지)로 판정한다. 부분 unique 인덱스 위반이 드라이버 어댑터 경유로 다른 오류 클래스로 와도 이 둘 중 하나면 통과
  - 인덱스 판정은 `pg_indexes.indexdef` 문자열 기준: trgm은 `USING gin` + `(title gin_trgm_ops)` / `("contentMd" gin_trgm_ops)`, 부분 unique는 `CREATE UNIQUE INDEX` + `("postId")` + ` WHERE ... "isCurrent"`. 인덱스 이름은 단정하지 않는다. `Post`에 `gin_trgm_ops` GIN 인덱스는 정확히 2개, `PostSlug` 부분 unique는 정확히 1개
  - 스키마 파일은 `backend/prisma/schema.prisma` 하나로 가정한다. `//`(및 `///`) 주석 밖에 `McpToken`·`mcpTokens` 문자열이 있으면 실패
  - seed: 글마다 `isCurrent=true` PostSlug가 정확히 1개이고 그 slug가 `Post.slug`와 같아야 하며, `PUBLISHED` 글이 1개 이상. 카테고리는 이름 기준 정확히 4개
  - `validateEnv`: `postgres://`(Testcontainers 형식)·`postgresql://`, TLD 없는 호스트(`localhost`, `127.0.0.1`), 쿼리 파라미터, 사용자·비밀번호 포함 URL을 통과시켜야 한다(class-validator `IsUrl` 기본 옵션은 이를 거부하므로 주의). `""`·`not-a-url`·숫자는 거부. 반환 객체에 `DATABASE_URL` 포함. 메시지에 값(비밀번호 포함) 미포함 — 다른 변수가 틀린 경우에도
  - health 503은 기존 전역 필터 형식으로 `code: 'SERVICE_UNAVAILABLE'`(Terminus의 `ServiceUnavailableException` → 필터 매핑)을 기대한다. e2e는 `NODE_ENV=test`, 닫힌 포트 `127.0.0.1:1`로 앱 생성·`init()`이 성공해야 하고(부팅 시 연결 금지), 요청당 20초 안에 503이 와야 한다. 로그에 DB 비밀번호가 찍히면 실패
  - Prisma 쿼리 인자 키 `data`가 ESLint `id-denylist`에 걸린다. 테스트는 협업 §10-a("정당한 예외는 주석으로 사유를 남기고 끈다")에 따라 해당 줄만 `eslint-disable-next-line id-denylist -- Prisma API 인자 이름`으로 껐다. seed·서비스 코드도 같은 문제가 생기므로 처리 방식(줄 단위 예외 vs 규칙 설정 조정 — 후자는 G2)을 ③·오케스트레이터가 정해야 한다

- 수동 SQL·drift 처리
  - 문제: 스키마가 모르는 인덱스를 마이그레이션 SQL에만 두면 `migrate dev`·`migrate diff`가 `DROP INDEX`를 drift로 낸다(부분 unique 인덱스를 스키마에서 뺀 상태로 실제 확인: `DROP INDEX "post_slug_current_unique"`가 나옴)
  - 처리: 인덱스 3개는 스키마에 선언해 Prisma가 SQL을 만들게 하고(이름은 §3.3과 같은 `post_title_trgm`·`post_content_trgm`), 스키마로 표현하지 않는 `pg_trgm` 확장만 마이그레이션 SQL에 직접 쓴다. Prisma는 `postgresqlExtensions` 프리뷰를 켜지 않으면 확장을 비교하지 않아 drift가 없다
  - 생성된 SQL: `CREATE INDEX "post_title_trgm" ON "Post" USING GIN ("title" gin_trgm_ops)`, `... "post_content_trgm" ... ("contentMd" gin_trgm_ops)`, `CREATE UNIQUE INDEX "post_slug_current_unique" ON "PostSlug"("postId") WHERE ("isCurrent" = true)`
  - drift 확인(실제 실행, 임시 `postgres:17.12` 컨테이너): ① 빈 DB에 `prisma migrate deploy` 성공, 다시 실행하면 `No pending migrations to apply.` ② `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code` → `No difference detected.`, exit 0 ③ `prisma migrate dev`(shadow DB 사용) → `Already in sync, no schema change or pending migration was found.`, 새 마이그레이션 없음 ④ `migrate status` → `Database schema is up to date!` ⑤ `migrate diff --from-empty --to-schema` 결과가 커밋한 마이그레이션의 생성 SQL 부분과 같음
  - ④·오케스트레이터 재확인 명령(backend 폴더, `DATABASE_URL`을 셸에 둔 상태): `pnpm exec prisma migrate deploy` → `pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code`(exit 0) → `pnpm exec prisma migrate dev`(새 마이그레이션 없음)

- 알아둘 점
  - **PostSlug 부분 unique의 클라이언트 함정**: `@@unique([postId], where: ...)` 때문에 생성 클라이언트가 `postSlug.findUnique({ where: { postId } })`를 허용하지만, Prisma는 이 조회에 `isCurrent` 조건을 붙이지 않는다(실측: 이전 slug 행이 나옴). 현재 slug는 `findFirst({ where: { postId, isCurrent: true } })`로 찾는다. 스키마 주석에 적어 둠. drift 없는 다른 표현(스키마에서 빼기, 비unique `@@index`, EXCLUDE 제약)은 drift가 생기거나 ② 테스트의 인덱스 정의와 맞지 않음
  - `partialIndexes`는 프리뷰 기능이다. Prisma 업그레이드 때 문법이 바뀌면 이 선언과 마이그레이션 diff를 함께 확인한다
  - `prisma.config.ts`가 `src/config/env.source.ts`를 import한다. 운영 컨테이너에서 `migrate deploy`를 돌릴 때(M0 Dockerfile 작업) 이 두 파일과 `prisma/`가 이미지에 있어야 한다
  - 통합 헬퍼의 Prisma CLI 자식 프로세스에는 `DATABASE_URL`·`CHECKPOINT_DISABLE`·`PRISMA_HIDE_UPDATE_MESSAGE`만 넘긴다(부모 `process.env`를 읽지 않음, ESLint 예외 없음). `node`는 `process.execPath` 절대 경로로 실행
  - seed CLI는 `DATABASE_URL`만 필요하다(`NODE_ENV`·`API_PORT` 불필요). 통합 테스트의 `runSeed`는 CLI를 거치지 않고 같은 `seedDatabase` 함수를 부른다
  - 503 응답의 `message`는 기존 전역 필터 규칙대로 5xx 공통 문구 `Internal server error`다(코드 `SERVICE_UNAVAILABLE`로 구분)
  - `pnpm add` 시 `@nestjs/terminus`의 선택 peer(`@grpc/grpc-js` 등)가 lockfile에 함께 기록됐다(이미 workspace에 있던 패키지)
