## 인계 노트

(단계별로 덧붙인다)

### ① OpenAPI 출력 (backend-dev)

- 명령: `pnpm --filter @jblog/backend openapi:generate` = `nest build && node dist/openapi/generate-openapi.js`. `tsx`는 esbuild라 `emitDecoratorMetadata`를 지원하지 않아 Nest DI가 깨지므로 빌드 결과를 실행한다. 출력 위치는 `backend/openapi.json`
- 구성: `src/openapi/generate-openapi.ts`(더미 환경값 상수, `createApp` → `createApiDocument(app)` → 파일 쓰기 → `app.close()`, listen·DB 연결 없음), `src/openapi/sort-keys.ts`(키 재귀 정렬, 배열 순서 유지). Swagger 제목·버전(`jblog API`·`1.0.0`)은 `bootstrap.ts`의 `createApiDocument` 한 곳에서 `/api/docs`와 공유
- 결정적 출력: 키 정렬 + `JSON.stringify(_, null, 2)` + 끝 줄바꿈. 두 번 실행해 바이트 동일 확인
- `/api/health`: Terminus `@HealthCheck()`가 200·503 스키마를 이미 문서화하므로 추가 데코레이터 없음. 문서의 503 본문은 Terminus 형태이고 실제 응답은 전역 필터의 에러 형식(`SERVICE_UNAVAILABLE`)이라 다르다(M2에서 에러 응답 문서화 시 정리)
- ②가 알아야 할 점(미해결): `JSON.stringify` 출력과 Prettier JSON 형식이 다르다(짧은 배열을 Prettier는 한 줄로 접는다). 커밋 훅(lint-staged)이 `openapi.json`에 `prettier --write`를 돌려 **커밋된 파일은 Prettier 형식**이고, 재생성하면 차이가 난다. 해결책은 `.prettierignore`에 `backend/openapi.json` 추가(devops 소유) 후 재생성한 파일을 커밋하는 것을 권장

### ② 생성 스크립트 (devops-engineer)

- 명령: `pnpm gen:api-types`(생성) · `pnpm gen:api-types --check`(비교, 종료 코드 0 일치 / 1 불일치·파일 없음 / 2 인자 오류, 파일 미변경). 구현은 `scripts/api-types/generate.mjs`, 시험은 `scripts/api-types/generate.test.mjs`(루트 `test:root`에 포함, 임시 폴더에서 `--source`·`--output`으로 시험). 생성 파일 머리에 자동 생성·원본·명령 주석
- 버전: `openapi-typescript` 7.13.0(정확한 버전, `frontend` devDependency). 루트에서는 frontend 기준 `createRequire`로 불러온다
- **peer 불일치(기록)**: 7.13.0(최신 안정, `next`는 7.0.0-rc.1뿐)은 peer `typescript ^5.x`라 TS 6.0.3과 맞지 않는다. pnpm 12는 설치를 실패시키지 않고 경고만 한다(`pnpm peers check`에 unmet peer 표시). 오케스트레이터 판단으로 예외 설정(`peerDependencyRules`)은 넣지 않았다. 근거: 기획 스택 그대로이고 CLI(생성기)로만 쓰며 생성물은 평범한 TS 선언. 확인: 생성물이 `frontend` tsc(TS 6.0.3)에 포함되어(`--listFiles`) 통과, 시험에서 `paths`에 `/api/health` 확인. **`openapi-typescript`가 TS 6을 지원하면 업그레이드하고 이 항목을 지운다.** 나중에 `pnpm peers check`나 `--strict-peer-dependencies`를 CI에 넣으면 이 경고가 걸리므로 그때 `peerDependencyRules.allowedVersions`(`openapi-typescript>typescript: '6'`)를 이유 주석과 함께 추가한다
- Prettier·ESLint: `.prettierignore`에 `backend/openapi.json`, `frontend/src/generated/` 추가(lint-staged가 파일 경로를 직접 넘겨도 `.prettierignore`를 따름을 확인: `prettier --write backend/openapi.json`이 무변경). ESLint ignores에 `frontend/src/generated/**`. 생성물은 git에 커밋. `openapi:generate`를 다시 실행하면 `git diff`가 없음(2회 동일, Prettier 무변경)
- `--check` 범위 결정: **생성 타입만 비교**한다(`openapi.json` → `api-types.ts`). 원본 재출력은 `nest build`를 포함해 느리고 backend 빌드 산출물에 의존하므로 `--check`에 넣지 않았다
- **CI(M0-08)에서 쓸 명령**: (1) `pnpm gen:api-types --check` (2) 원본 최신 여부는 `pnpm --filter @jblog/backend openapi:generate && git diff --exit-code backend/openapi.json`(별도 단계, backend 빌드 뒤). 둘 다 `pnpm install` 뒤에 실행한다. 제안(backend-dev 몫): `openapi:generate --check`가 필요하면 backend 스크립트에 추가
- ③이 알아야 할 점: 생성 타입은 `@/generated/api-types`에서 `paths`·`components`·`operations`를 import한다. `frontend/tsconfig.json`의 `src/**/*.ts`에 이미 포함된다. `src/generated/**`는 ESLint 제외라 lint 규칙(any 등)이 적용되지 않는다. 계약이 바뀌면 `pnpm gen:api-types`를 다시 실행해 같은 커밋에 넣는다

### ③ 프론트엔드 연결 (frontend-dev)

- 의존성: `openapi-fetch` 0.17.0(정확한 버전, `frontend` dependencies). peer 없음
- `frontend/src/lib/api/server.ts`: `import 'server-only'`, `createServerApi(cacheTags = [])`가 `createClient<paths>`를 만든다. baseUrl은 `env.server.API_INTERNAL_URL`. 캐시 태그는 호출마다 달라 클라이언트 생성 시점에 받아 openapi-fetch의 `requestInitExt`(`{ next: { tags } }`)로 `fetch`에 넘긴다(Request 객체로는 `next` 확장이 전달되지 않아 이 옵션을 쓴다). `/internal/*` 원문 헤더(`X-Internal-Key`)는 해당 API가 생기는 M2 이후 추가
- `frontend/src/lib/api/client.ts`: `browserApi = createClient<paths>({ baseUrl: '' })`(같은 오리진 상대 경로). 인증·CSRF·refresh는 M3
- 타입 연결 확인: 임시 파일(삭제함)에서 `browserApi.GET('/api/health')`의 `data.status`가 생성 타입(`'ok' | 'degraded'`)으로 추론되고, 없는 경로(`/api/nope`)는 `@ts-expect-error`가 필요한 오류가 됨을 `tsc`로 확인
- lint: 사용처가 없어도 export된 모듈이라 ESLint가 문제 삼지 않음(규칙 변경 없음)
- 검사: frontend `test` 22 통과, 더미 환경변수로 `build` 통과, `test:e2e` 3 통과, 루트 `lint`·`format:check`·`typecheck`·`test` 통과, `gen:api-types --check` 0

### Codex r1 대응 (backend-dev)
