## 테스트 대상 인터페이스 (③ 테스트 선작성 기준, 오케스트레이터 확정)

테스트는 아래 진입점만 쓴다. 구현(④)은 이 시그니처를 지킨다. 테스트 코드는 `process.env`를 쓰지 않고(ESLint 금지) 환경값을 인자로 넘긴다.

| 경로 | 내보내는 것 | 동작 |
|---|---|---|
| `backend/src/config/env.validation.ts` | `validateEnv(raw: Record<string, unknown>): AppEnv`, 타입 `AppEnv` | 규약 4 검증. 실패하면 `Error`를 던지고 메시지에 문제 변수 이름을 모두 담는다(값은 담지 않는다) |
| `backend/src/config/env.source.ts` | `readProcessEnv(): Record<string, unknown>` | `process.env`를 읽는 유일한 함수. `main.ts`만 쓴다 |
| `backend/src/bootstrap.ts` | `createApp(rawEnv: Record<string, unknown>, options?: CreateAppOptions): Promise<INestApplication>` | `validateEnv(rawEnv)` 후 규약 5~8을 모두 적용한 앱을 만든다(**listen하지 않음**, 호출 측이 `init()`/`listen()`). 앱 동작은 `rawEnv`로만 결정되고 주변 `process.env`에 의존하지 않는다. 검증 실패 시 reject |
| 〃 | `CreateAppOptions = { imports?: ModuleImports; logStream?: NodeJS.WritableStream }` | `imports`: 테스트용 모듈(예외를 던지는 컨트롤러, DTO 검증 라우트)을 `AppModule`과 함께 등록. `logStream`: pino 출력 대상(테스트가 로그를 읽어 redact 확인) |
| `backend/src/common/errors/app.exception.ts` | `AppException(status: HttpStatus, code: string, message: string)` | 규약 7의 코드 지정 앱 예외 |
| `backend/src/main.ts` | — | `createApp(readProcessEnv())` → `listen(API_PORT)` |

기본 에러 코드: 404 `NOT_FOUND`, 400 `BAD_REQUEST`, ValidationPipe 실패 400 `VALIDATION_FAILED`, 알 수 없는 오류 500 `INTERNAL_ERROR`. 그 밖의 상태는 `HttpStatus` 이름(예: 401 `UNAUTHORIZED`, 409 `CONFLICT`).

Jest 실행: `--experimental-vm-modules` 필요(Nest 12가 ESM 전용, ② 인계 노트). 패키지 스크립트로 실행한다.

- 변경 요약: `backend/jest.config.mjs`(단위 `src/**/*.spec.ts`), `jest.config.e2e.mjs`(e2e `test/**/*.e2e-spec.ts`), 공유 `jest.config.base.mjs`, `test/setup.ts`(`reflect-metadata` 로드), `backend/.env.example`(규약 9), `backend/package.json`의 `test`·`test:e2e`와 테스트 devDependencies, `pnpm-workspace.yaml`의 `allowBuilds`, `pnpm-lock.yaml`. 루트 `eslint.config.mjs`는 변경 없음(spec의 `describe`·`jest` 전역은 기존 규칙에서 오류가 나지 않았다)

| 패키지 | 버전 |
|---|---|

- 변환기 선택 이유: `ts-jest`. peer가 TS 6을 포함하고, 타입 검사와 `emitDecoratorMetadata`를 tsconfig 그대로 처리한다. `@swc/jest`는 네이티브 바이너리(`@swc/core`)가 추가되고 데코레이터 메타데이터 설정이 따로 필요해 택하지 않았다
- 명령: `pnpm --filter backend test`(단위), `pnpm --filter backend test:e2e`, 루트 `pnpm test`(turbo가 backend `test` 실행). 둘 다 `--passWithNoTests`
- 검사: 임시 spec(`@nestjs/testing`으로 DI 생성자 주입) 단위·e2e(Supertest) 통과 후 삭제. `pnpm lint`, `format:check`, `typecheck`, `test`, backend `test`·`test:e2e`(테스트 0건) 모두 통과. `.env` 없이 실행
- 알아둘 점
  - **Nest 12 패키지는 ESM-only(`"type": "module"`)** 이다. Jest가 CJS 테스트에서 이를 `require`하려면 Node의 `--experimental-vm-modules`가 필요해서(Jest 30 + Node 24.9+) 스크립트를 `node --experimental-vm-modules node_modules/jest/bin/jest.js ...`로 썼다. 실행 시 ExperimentalWarning 한 줄이 나오며 정상이다. IDE·`npx jest`로 직접 돌릴 때는 `NODE_OPTIONS=--experimental-vm-modules`가 필요하다
  - 설정 파일을 `.mjs`로 둔 이유: 루트 ESLint가 `require()`를 금지한다. e2e 설정은 소유권(`backend/jest.config.*`) 때문에 `test/`가 아닌 `backend/jest.config.e2e.mjs`에 있다
  - `allowBuilds`: 기존 `@scarf/scarf: false`(swagger-ui-dist 텔레메트리 스크립트 거부)는 타당해서 유지한다. 소유자(devops) 확인 완료. 새 의존성에서 `@parcel/watcher`(jest-haste-map 전이, `--watch` 전용, 스크립트는 네이티브 빌드 폴백)가 같은 `ERR_PNPM_IGNORED_BUILDS`를 일으켜 같은 방식(`false`)으로 추가했다
  - 테스트는 `backend/.env`를 읽지 않는다. 필요한 환경변수는 테스트 코드에서 `process.env`가 아니라 설정 모듈에 직접 주입하는 방식으로 넣는다(③ test-engineer 참고)
