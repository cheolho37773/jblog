## 동작 규약 (오케스트레이터 확정)

| # | 항목 | 규약 |
|---|---|---|
| 1 | 환경변수 | 백엔드 환경 검증(`env.validation.ts`)에 `INTERNAL_API_KEY`를 **필수**로 넣는다(문자열, 16자 이상). 없거나 짧으면 기동이 실패하고, 메시지에는 이름만 담는다. 기존 테스트·`build:verify`·Docker 빌드가 깨지지 않게 테스트 부팅 환경에 더미 값을 둔다 |
| 2 | `InternalKeyGuard` | `X-Internal-Key` 헤더를 `INTERNAL_API_KEY`와 **상수 시간 비교**(`crypto.timingSafeEqual`, 길이가 달라도 안전하게)로 확인한다. 없음·빈 값·불일치는 공통 에러 형식 **401** `UNAUTHORIZED`다. 응답·로그에 키 값이나 비교 결과 세부를 담지 않는다. 내부 컨트롤러에만 붙인다 |
| 3 | 응답 | `GET /internal/posts/{slug}`<br>• 공개 글(M2-03 공개 조건과 같음)이면 `InternalPostResponseDto`를 돌려준다. `post`는 메타 + `contentMd` + `version`, 그리고 `prev`·`next`·`related`(M2-03과 같은 규칙)<br>• 이전 slug면 **200 `{ redirectTo: <현재 slug> }`**(대상이 공개 글일 때만, 아니면 404)<br>• 없거나 비공개면 404 `POST_NOT_FOUND`<br>• 가드가 먼저 돈다. 키가 틀리면 slug 존재 여부와 관계없이 401이다 |
| 4 | 스냅샷 | 본문·메타·prev/next/related를 **읽기 전용 `REPEATABLE READ` 트랜잭션 하나**에서 읽는다(백엔드 §4.5·§5.8). 여러 조회가 서로 다른 시점을 보지 않게 하기 위해서다. 공개 조건·정렬은 M2-03의 정의를 그대로 재사용한다(중복 정의 금지) |
| 5 | 캐시 헤더 | 200·401·404 모두 `Cache-Control: private, no-store` |
| 6 | 로그 마스킹 | 요청 로그 redact 경로에 `req.headers["x-internal-key"]`를 추가한다. 정상 요청과 401 요청 **모두** 로그에 키 값이 없어야 한다 |
| 7 | 경로 | `/api/internal/*`은 404다(M2-01). 내부 API는 전역 prefix 밖에 둔다 |

### ② 구현 (backend-dev)

- 가드 비교 방식: `X-Internal-Key`와 `INTERNAL_API_KEY`를 각각 SHA-256으로 해시한 뒤 `crypto.timingSafeEqual`로 비교한다(해시 길이가 같아 길이가 달라도 안전). 없음·빈 값·불일치는 401 `UNAUTHORIZED`이고 메시지에 값·비교 세부는 없다. 가드가 `Cache-Control: private, no-store`를 먼저 붙이고, `AllExceptionsFilter`는 이미 `no-store`가 있으면 덮어쓰지 않는다(공개 API 오류의 `no-store`는 그대로).
- 트랜잭션: `$transaction(async tx => ...)` + `isolationLevel: RepeatableRead`. Prisma 7에는 읽기 전용 옵션이 없어 첫 쿼리 전에 `SET TRANSACTION READ ONLY`(`$executeRaw`)를 실행한다(BEGIN 직후·첫 쿼리 전이면 PostgreSQL이 허용). 모든 조회는 `tx`로, 한 연결이므로 순차 실행한다.
- 재사용 구조: 신규 `published-post-queries.ts`(`findNeighbor`·`findRelated`·`findCurrentSlugOfOldSlug`, 첫 인자 `PostDb = PrismaClient | TransactionClient`). `PostsService`(공개)는 `this.prisma`, `InternalPostsService`는 `tx`를 넘긴다. 공개 조건·정렬은 `published-post.ts` 그대로. 공개 API 동작 불변.
- 환경: `INTERNAL_API_KEY` 필수(`@IsString @MinLength(16)`), 로그 redact에 `req.headers["x-internal-key"]`, `OPENAPI_ENV`·`createIntegrationEnv`에 더미 키. `build:verify`·Docker 빌드는 키 없이 통과.
- 검사: `test` 57, `test:e2e` 91 통과. `pnpm verify`(contract:check 포함, openapi.json 불변)·`pnpm docker:build` 통과. `test:integration` 191 통과 / **4 실패**: 모두 `internal-posts.int-spec.ts`의 "키 헤더 없음 + (4개 slug)" 케이스. 원인은 테스트 버그다: `getInternal(path, key = TEST_INTERNAL_KEY)`의 기본값 때문에 `undefined`를 넘겨도 올바른 키가 실려 헤더가 없는 요청이 되지 않는다(200/404가 나옴). Test Agent 수정 요청: 기본값을 없애거나 "헤더 없음"을 별도 표기로 구분.
