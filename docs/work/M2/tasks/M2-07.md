## 동작 규칙 (오케스트레이터 확정)

| 항목 | 규칙 |
|---|---|
| 쿼리 | `category`, `tag`, `page`만 쓴다. `category`와 `tag`가 함께 오면 **`tag`가 우선**하고 `category`는 무시한다. 칩 링크는 `tag`·`page`를 붙이지 않고, 태그 해제 칩은 `/blog`다 |
| 없는 slug | `category`·`tag` slug가 `/api/categories`·`/api/tags` 목록에 없으면 `notFound()`(404). `postCount` 0인 카테고리는 있는 slug라 빈 상태로 그린다 |
| `page` 값 | 1 이상의 정수가 아니면 1로 본다. `totalPages`보다 크면 `totalPages`로 줄인다(글이 0개면 1). 주소는 바꾸지 않는다(서버 리다이렉트 없음) |
| `?page=n` 새로고침 | 서버가 1~n 페이지(각 `size=9`)를 병렬로 조회해 차례대로 이어 그린다. 이어 붙일 때 **slug 기준 중복 제거**(앞에 나온 것을 남김) |
| Overlay와 그리드 | 그리드는 API 페이지를 그대로 보여 준다. Overlay 글이 그리드 첫 페이지에 다시 나와도 빼지 않는다(그리드가 9개로 꽉 차고 `?page=` 계산이 API 페이지와 일치하도록). 오케스트레이터 판정 |
| Load More | 클라이언트 컴포넌트가 `browserApi`로 `/api/posts?page={현재+1}&size=9`(+ 같은 `category` 또는 `tag`)를 부른다. 받은 글은 slug 기준 중복 제거 후 뒤에 붙인다. 성공하면 `history.replaceState`로 `?page=`를 갱신한다(다른 쿼리는 유지). 마지막 페이지에 도달하면 버튼을 없앤다 |
| Load More 진행·실패 | 요청 중에는 버튼 `disabled` + `aria-busy="true"`(중복 클릭 방지). 실패하면 목록은 그대로 두고 버튼 위에 `role="alert"` 오류 문구 `글을 더 불러오지 못했습니다. 다시 시도해 주세요.`를 보여 주며 버튼으로 재시도한다. 성공 시 `aria-live="polite"` 영역에 `글 {n}개를 더 불러왔습니다.` |
| Load More 후 포커스 | 포커스는 버튼에 그대로 둔다. 버튼이 사라지면 새로 붙은 첫 카드 링크로 옮긴다 |
| 빈 상태 | 글이 0개면 그리드·Load More 대신 `아직 글이 없습니다` + Home(`/`) 링크(UI §7.2). 필터 상태에서도 같은 문구다. Overlay 없음 |
| 조회 실패 | 서버 조회(목록·카테고리·태그) 5xx·네트워크 오류는 빈 목록으로 바꾸지 않고 오류로 끝낸다(기존 `throwOnServerError`) |
| 캐시 | 서버 조회는 `createServerApi(['posts'])`(태그 `posts`, `revalidate: 3600`). 페이지는 요청 시 렌더한다(`connection()`, 프론트 §4 "빌드와 데이터"). Footer 카테고리 조회도 같다 |
| 빌드 | 일반·Docker 빌드가 백엔드 없이 통과해야 한다(기존 build-verify, 닫힌 포트 4999). Footer 조회 때문에 `(site)` 정적 페이지가 빌드 중 API를 부르면 안 된다 |
| `loading.tsx` | `/blog`에 둔다. PageInfo(`Blog`) + 칩 자리 없이 `PostCardSkeleton` 9개를 같은 그리드로 |
| 메타데이터 | `title`: 기본 `Blog`, 카테고리 `{카테고리명} · Blog`, 태그 `#{태그명} · Blog`(루트 title 템플릿을 따른다). canonical은 M2-08에서 다룬다 |

  - 마지막 페이지 판정은 Props `totalPages`와 현재 페이지로 한다. 버튼이 사라지면 포커스는 **새로 붙은 첫 카드 링크**(E2E는 `/blog/{13개 중 10번째 slug}`가 `:focus`). 버튼이 남으면 버튼 유지
  - data-testid 요구(E2E)
    - `blog-empty`: 빈 상태 컨테이너. `아직 글이 없습니다` 문구와 `a[href="/"]` 하나를 안에 둔다(Breadcrumb의 Home과 구분)
    - `blog-loading-grid`: `loading.tsx` 스켈레톤 그리드. **직계 자식이 정확히 9개**이고 각 자식은 `aria-hidden="true"`이거나 그런 요소를 포함한다. 같은 화면에 `h1` `Blog`, 칩 nav·Load More는 없다
  - DOM 계약: Overlay = `main article` 중 `h2`를 가진 것(그리드 카드는 `h3`). Overlay 링크는 `/blog/{featured slug}`. 그리드는 `ul[aria-label="글 목록"] > li`이고 카드 링크(`a`)가 li 안에 있다. 칩 nav는 `nav[aria-label="카테고리"]`, 태그 해제 링크는 이름 `#태그명 필터 해제`·`href="/blog"`·안에 `aria-hidden="true"` 요소(✕). 태그 필터에서는 칩 nav가 없다. Breadcrumb는 기존 `nav[aria-label="현재 위치"]`의 `li` 3개(`Home`·`Blog`·`#Next.js`)
  - 측정 기준
    - 세로 간격은 요소 사각형(getBoundingClientRect) 기준 ±1px: Navbar(`header`) 하단→PageInfo 루트(`h1`의 부모) 상단 24, PageInfo 하단→**첫 칩 링크**(보이는 칩) 상단 24, 칩 링크 하단→Overlay 루트 상단 48, Overlay 하단→`ul` 상단 48, `ul` 하단→Load More 버튼 상단 32. 칩 nav의 위아래 여백(py-2 8px)은 간격에 넣지 않으므로 구현에서 그만큼 줄여야 한다(예: 상단 `mt-4`·하단 `mb-10` 식). 태그 필터는 PageInfo→해제 칩 24, 해제 칩→`ul` 48
    - 그리드: 같은 top의 `li` 개수=열 수(1440·1024=3, 768=2, 375=1). 첫 `li` 오른쪽→둘째 `li` 왼쪽=열 gap(20·20·20), 둘째 행 top − 첫 `li` bottom=행 gap(16은 375). 한 행의 카드 링크(`a`) 높이 차 ≤0.5px이고 카드 링크 하단이 `li` 하단과 같다(카드가 행을 채움, `a`가 `h-full` 등으로 늘어난다)
  - 동작 해석: Overlay는 `/blog`·`/blog?page=1`·`?page=0|abc|-3|1.5`(=1페이지)에만 나온다. `?page=2`·`?page=99`(→2)는 Overlay 없음, 13개, Load More 없음, 주소 불변. 그리드 1페이지 9개에 Overlay 글(최신순 3번째)이 다시 포함돼 `main`에 그 글 링크가 2개다(오케스트레이터 판정대로). `category`+`tag`가 같이 오면 tag만(없는 category는 404 아님, 없는 tag는 category가 있어도 404). Footer: 모든 `(site)` 페이지(`/`, `/search`, `/blog…`)에서 `footer`(contentinfo) 안 `a[href^="/blog?category="]`가 `/api/categories` 순서의 `postCount>0` 앞 6개(현 픽스처는 정확히 6개라 빈 카테고리가 앞에 있어도 `slice(0,6)`만으로는 실패)
  - 서버 조회 실패: `/blog?tag=fixture-error`가 **응답 상태 5xx**여야 한다(요청 응답 상태를 본다). 주의: `loading.tsx`가 있으면 스트리밍이 먼저 시작돼 상태가 200으로 굳을 수 있다. 구현에서 그렇게 되면 임의로 테스트를 바꾸지 말고 보고할 것(오케스트레이터가 지시서·테스트 기준을 정한다)
- 확인 방법과 한계
  - loading 스켈레톤: 서버 fetch는 브라우저를 거치지 않아 `page.route`로 지연할 수 없어, 픽스처의 지연 태그(`/blog?tag=fixture-slow-N`, 3초)로 `goto(..., { waitUntil: 'commit' })` 뒤 스켈레톤을 본다. 스트리밍이 프록시·압축에서 버퍼링되면 불안정할 수 있어, 그 경우 보고한다
  - 빈 **태그**(글 0개 태그)와 필터 상태의 빈 문구는 E2E 픽스처로 만들 수 없어 단위·구현 확인에 맡긴다(빈 카테고리 화면은 E2E 확인)
  - Footer의 "앞 6개로 자르기"는 현 픽스처(글 있는 카테고리 6개)로는 7번째 이후를 볼 수 없다(기존 `Footer.spec.tsx`가 6개 상한을 이미 확인)
  - 일반·Docker 빌드의 백엔드 없는 통과는 기존 build-verify가 본다(새 테스트 없음)
