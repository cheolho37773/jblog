# M0-04 검수 r1

## 종합 판정

수정 후 통과 — 500 HTTP 예외의 내부 메시지 노출과 Swagger 요청의 요청 ID 누락을 확인했다. 두 문제의 수정 및 회귀 테스트가 필요하다.

## 지적 사항

### 1. [높음] 500 HTTP 예외가 내부 메시지를 노출하고 오류 로그를 생략한다

- 위치: `backend/src/common/filters/all-exceptions.filter.ts:48`
- 근거: `docs/work/M0/tasks/M0-04.md` 동작 규약 7은 내부 메시지를 응답에 넣지 않고 500 오류를 서버 로그에 남기도록 요구한다. 현재 `HttpException` 분기는 상태와 관계없이 `exception.message`를 반환하고 로깅 전에 종료한다. 이는 `docs/plan/00_overview.md` §6-b의 민감 정보 출력 금지에도 저촉될 수 있다.
- 영향: `InternalServerErrorException` 또는 상태 500의 `HttpException`·`AppException`에 내부 오류 설명을 담으면 클라이언트에 그대로 노출된다. 소스 코드를 메모리에서 변환해 필터를 직접 호출한 결과, 더미 내부 메시지가 응답에 포함되고 오류 로그 호출은 0회였다. 기존 테스트는 일반 `Error`만 검증하므로 이 경로를 놓친다.
- 권고: 500 상태는 `HttpException` 여부와 관계없이 일반 메시지로 응답하고 원래 예외를 서버 로그에 기록한다. 세 HTTP 예외 유형에 대해 메시지 비노출과 로깅을 확인하는 회귀 테스트를 추가한다.

### 2. [중간] Swagger 요청이 요청 ID 미들웨어를 거치지 않는다

- 위치: `backend/src/bootstrap.ts:17`
- 근거: `docs/work/M0/tasks/M0-04.md` 동작 규약 8과 `docs/plan/01_backend_plan.md` §6은 요청 ID를 전파·생성하고 응답 헤더로 반환하도록 요구한다. Swagger 라우트는 `createApp()`에서 등록되지만, `nestjs-pino` 요청 미들웨어는 이후 앱 초기화 단계에서 등록된다.
- 영향: 초기화된 앱의 Express 핸들러를 메모리 내 요청·응답 객체로 호출해 확인했다. 동일한 `x-request-id`를 보냈을 때 `/api/docs`는 200이지만 응답에 요청 ID가 없었고, 일반 404 경로는 정상 반환했다. 기존 요청 ID 테스트는 Swagger 경로를 검증하지 않는다.
- 권고: Swagger 경로에도 요청 로깅과 요청 ID 처리가 먼저 적용되도록 등록 순서를 조정한다. `/api/docs`에서 요청 ID 전달·생성을 확인하는 테스트를 추가한다.

- 지정한 base~head의 변경 파일 목록과 diff: 백엔드 소스·설정·테스트, `.env.example`, 작업 지시서, 마스터 체크리스트, `pnpm-workspace.yaml`, `pnpm-lock.yaml`.
- 기준 문서: `AGENTS.md`, 개요 §2.1·§6·§6-a·§6-b, 백엔드 §2·§4.1·§6·§7, 협업 §5.2·§10-a·§10, M0-04 지시서.
- 루트 설정과 커밋별 변경 경로·역할 trailer를 대조했다. 설정 모듈 밖 `process.env` 접근과 변경분의 실제 비밀값 하드코딩은 발견하지 못했다.
- 통과: 백엔드·루트 TypeScript `--noEmit`, 루트 ESLint, Prettier 검사, 루트 ESLint 규칙 테스트 48건, `git diff --check`.
- 직접 재현: HTTP 예외 유형별 500 응답·로깅, Swagger와 일반 경로의 요청 ID 반환 차이. 소스 변환은 메모리에서만 수행했다.
- 검증 제한: Jest 단위·e2e는 `--no-cache --runInBand`로 시도했으나 읽기 전용 환경에서 haste-map 캐시 쓰기가 `EPERM`으로 차단되어 실행되지 않았다. 빌드와 실제 포트 기동은 수행하지 않았다.
- 코드·문서 파일은 수정하지 않았다.
