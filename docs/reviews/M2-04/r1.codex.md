# M2-04 검수 r1

## 종합 판정
수정 후 통과 — 인증·캐시·로그 마스킹과 읽기 전용 트랜잭션은 요구사항에 부합한다. 다만 예약 발행 경계를 지나는 요청에서는 공개 여부의 시간 기준이 달라져 응답의 시점 일관성이 깨질 수 있다.

## 지적 사항

### 1. [중간] 트랜잭션 내 조회마다 공개 기준 시각을 다시 계산한다
- 위치: `backend/src/modules/posts/internal-posts.service.ts:47`, `backend/src/modules/posts/published-post-queries.ts:39`, `backend/src/modules/posts/published-post-queries.ts:56`
- 근거: `docs/work/M2/tasks/M2-04.md` 동작 규약 4와 `docs/plan/01_backend_plan.md` §4.5는 본문·메타·prev/next/related가 한 시점을 보도록 요구한다. 현재 각 조회는 `publishedPostWhere()`를 별도로 호출하며, 이 함수는 매번 `new Date()`로 공개 기준 시각을 생성한다. `REPEATABLE READ`로 DB 스냅샷을 고정해도 애플리케이션에서 전달하는 시간 조건은 고정되지 않는다.
- 영향: `next` 조회와 `related` 조회 사이에 같은 카테고리 글의 예약 발행 시각이 도달하면, 해당 글이 `next`에서는 제외되고 `related`에는 포함된다. 소스를 메모리에서 변환해 시계·DB 대역으로 실행한 결과, 조회 기준 시각이 각각 0·1·2·3초로 달라졌으며 2.5초에 발행되는 글에 대해 `next: null`, `related: ["scheduled"]`가 재현됐다.
- 권고: 내부 상세 조회에서 공개 기준 시각을 한 번 정하고 본문·이전 slug·이전/다음·관련 글 조회에 같은 값을 전달한다. 예약 발행 시각을 조회 도중 통과하는 경우를 스냅샷 회귀 테스트에 추가한다.

## 확인한 범위

- 지정 base~head의 변경 파일 목록과 구현·테스트·작업 기록 diff를 검토했다. HEAD는 지정 SHA와 일치했다.
- M2-04 지시서와 기준 문서의 내부 API, 공개 조건, 인증, 캐시, 동시 실행, 민감 정보, 소유권 규칙을 대조했다.
- 가드의 상수 시간 비교, 환경변수 검증, 키 마스킹, 내부 응답 DTO, 공개 조회 로직 재사용, 트랜잭션 범위 및 필수 검증 테스트를 확인했다.
- `git diff --check`는 통과했다.

- 통합 테스트·Docker 빌드·`pnpm verify`·`contract:check`는 실행하지 않았다. 작업 지시서에 기록된 통과 주장은 독립 검증 근거로 사용하지 않았다.
