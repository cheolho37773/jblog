# M2-plan 검수 r1

## 종합 판정

수정 후 통과 — 내부 API 키의 로그 마스킹, 픽스처 실행 환경의 담당·선행 작업, 정적 생성 도입에 따른 빌드 검증 방식을 계획에 보완해야 한다.

## 지적 사항

### 1. [높음] 내부 API 키 도입에 요청 로그 마스킹이 빠짐

- 위치: `docs/work/M2/plan.md:44`
- 근거: `docs/plan/00_overview.md` §6-b는 비밀값의 로그 출력을 금지하고 pino redact 적용을 요구한다. 현재 `backend/src/common/logging/logger.options.ts:10`은 authorization·cookie·set-cookie만 가린다. M2-04에는 `X-Internal-Key` 도입과 인증 테스트가 있지만 로그 마스킹 작업·검증은 없다.
- 영향: 현재 로깅 설정을 유지한 채 내부 API를 구현하면 SSR 요청에 실린 내부 키가 요청 로그에 기록될 수 있다. 브라우저 번들 검사만으로는 이를 검출하지 못한다.
- 권고: M2-04에 내부 키 헤더의 로그 마스킹을 포함한다. 정상·인증 실패 요청 모두에서 테스트용 키가 로그에 남지 않는 검증을 필수 항목으로 추가한다.

### 2. [중간] 픽스처 API 실행 환경을 만들 선행 작업과 담당이 없음

- 위치: `docs/work/M2/plan.md:108`
- 근거: `docs/plan/05_collaboration_architecture.md` §4.3-a·§5.2에서 Playwright 공통 설정은 DevOps 담당이다. 현재 `frontend/playwright.config.ts`는 응답 서버가 없는 더미 API 주소와 standalone 서버를 사용한다. 그러나 작업 목록에서 DevOps 참여는 M2-01의 `.env.example` 변경뿐이며, 픽스처 서버 연결을 담당할 작업이 없다. §6 결정 1의 DevOps 언급도 실제 스택의 CI 스모크에 한정된다.
- 영향: 화면 작업이 사용하는 픽스처 서버의 기동·종료와 API 연결이 준비되지 않는다. 특히 standalone에서는 개발용 `/api` rewrite가 적용되지 않아 RSC 조회만 연결해도 브라우저의 Load More 요청은 실패할 수 있다.
- 권고: 첫 데이터 연동 화면 작업 전에 Test·Frontend·DevOps가 참여하는 환경 작업을 배정한다. 픽스처 작성, 빌드 전 서버 기동, RSC·브라우저 요청 연결, 일반 E2E·시각 회귀 실행 검증을 완료 기준으로 명시한다.

### 3. [중간] 정적 생성에 필요한 데이터를 일반·Docker 빌드에 공급할 방법이 없음

- 위치: `docs/work/M2/plan.md:48`
- 근거: `docs/plan/02_frontend_plan.md` §4는 상세의 최근 50개 사전 생성을 요구하고, 협업 §4.2·§10은 빌드와 CI 통과를 요구한다. 현재 루트 `build:verify`는 응답 서버가 없는 더미 주소를 사용하고, `frontend/Dockerfile`도 백엔드 없이 frontend를 빌드한다. 계획의 픽스처 서버는 Playwright `webServer`에만 연결되어 있다.
- 영향: `generateStaticParams`와 Home의 데이터 조회가 추가되면 일반 빌드·Docker 빌드에도 API가 필요해진다. E2E가 통과해도 `pnpm verify`와 CI의 `build`·`docker` 잡이 실패할 수 있다.
- 권고: 빌드 시 데이터 공급과 내부 키 주입 방식을 별도로 정하고 담당 작업을 배정한다. 백엔드가 없는 깨끗한 환경에서 일반·Docker 빌드를 검증하고, 실행 시 실제 API 연결도 확인한다. 조회 실패를 빈 목록으로 삼켜 빌드를 통과시키는 방식은 피한다.
