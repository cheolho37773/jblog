# 블로그·포트폴리오 기획 2차 검토 피드백

> 검토일: 2026-11-20
> 검토 범위: 개정된 `docs/plan` 기획문서 5개와 `docs/ui_design/ui_design_spec.md`
> 이전 검토: [1차 기획 검토 피드백](./2026-11-20_plan_review.md)
> 이 문서는 기획에 명시된 동작과 문서 간 정합성을 기준으로 작성했다. 구현 코드에서 결함을 확인한 결과는 아니다. 기존 기획문서와 1차 피드백은 수정하지 않았다.
> 근거 위치는 2차 검토 당시 문서 기준이며, 이후 개정 시 달라질 수 있다.

## 1. 종합 의견

이전 피드백은 대부분 반영됐고 구현 준비도가 높아졌다. 작업본 분리, 내부 API 분리, 조회수 집계, 토큰 즉시 차단이 구체화됐다.

다만 추가된 비공개 미디어와 캐시 설계에서 중요한 문제가 발견됐다. M3 구현 전에는 작업본 계약과 캐시 갱신·복구 기준을 확정하고, M7 전에는 비공개 미디어의 인증·캐시·이미지 최적화 경로를 다시 설계해야 한다.

## 3. 먼저 해결할 사항

### 3.1 [높음·M7] 비공개 미디어 인증 캐시의 권한 혼합 위험

**근거:** [AI 기획서 §4.3](../03_ai_authoring_mcp_plan.md), 검토 당시 152행

미디어 인증 결과를 60초 캐시하고, 캐시 키에 쿠키 유무를 포함한다. 쿠키가 있다는 사실은 인증 성공을 의미하지 않는다. 관리자와 임의·만료 쿠키를 가진 요청이 같은 캐시 키를 사용하면 관리자의 허용 결과가 재사용될 수 있다.

**권고:** 관리자 인증 결과는 캐시하지 않는다. 공개 여부만 미디어 ID 기준으로 캐시하고, 비공개 파일은 매 요청 세션과 `tokenVersion`을 검사하면 단순하다.

같은 항목에서 인증 실패를 404로 반환하도록 했지만, `auth_request`는 2xx를 허용, 401·403을 거부로 처리하고 그 밖의 상태는 오류로 취급한다. 인증 서브요청은 401·403을 반환하고 외부 응답을 404로 변환해야 한다. [Nginx 공식 문서](https://nginx.org/en/docs/http/ngx_http_auth_request_module.html)

### 3.2 [높음·M7] 비공개 이미지와 Next.js 이미지 최적화의 연결 누락

**근거:** [백엔드 §5.5](../01_backend_plan.md), 검토 당시 542행 / [AI 기획서 §4.3](../03_ai_authoring_mcp_plan.md)

이미지 처리는 Next.js Image Optimization을 사용하지만 비공개 이미지는 관리자 쿠키를 요구한다. 기본 이미지 최적화기는 원본 요청에 인증 헤더를 전달하지 않으므로 관리자 프리뷰의 비공개 이미지가 표시되지 않을 수 있다.

**권고:** 비공개 이미지는 `unoptimized`로 브라우저가 직접 인증 요청하도록 하는 방식을 우선 검토한다. [Next.js 공식 문서](https://nextjs.org/docs/app/api-reference/components/image)

또한 공개 → 비공개 전환과 1년 `immutable` 캐시는 함께 충족하기 어렵다. 이미 배포된 브라우저 캐시와 최적화 이미지가 남기 때문이다. 공개 철회가 향후 원본 접근만 막는 것인지, 캐시된 파생 이미지까지 회수하려는 것인지 구분해야 한다.

### 3.3 [높음·M3] 발행 후 1분 이내 일치 기준의 불충분한 보장

**근거:** [프론트엔드 §4](../02_frontend_plan.md), 검토 당시 110~131행

캐시 원칙은 시간 기반 재검증을 쓰지 않는다고 설명한 뒤 `revalidate: 3600`을 안전망으로 둔다. ‘이벤트 기반 갱신을 기본으로 하고 시간 기반 갱신을 보조로 사용한다’로 정리하는 것이 정확하다.

webhook 예시의 `revalidateTag(t)`는 검토 시점 최신 공식 문서에서 폐기 예정인 단일 인자 방식이다. 즉시 만료가 필요한 webhook에는 `{ expire: 0 }` 같은 정책을 명시해야 한다. webhook은 이미 열린 브라우저 화면을 즉시 갱신하지도 않는다. [Next.js 공식 문서](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)

**권고:** 완료 기준을 다음처럼 나눈다.

- 서버에서 캐시 무효화가 완료되는 시간
- 완료 이후 새 요청이 최신 데이터를 받는 조건
- 이미 열린 화면·Load More 결과의 갱신 방식

브라우저 API 캐시도 별도이므로 서버 태그 무효화만으로 모든 화면이 동시에 일치하지는 않는다. 시간 기반 안전망도 요청 시점과 갱신 방식에 따라 동작하므로 엄밀한 최대 노출 지연으로 표현하지 않는다.

### 3.4 [높음·M3] DB 커밋 후 프로세스 종료 시 이벤트 유실

**근거:** [백엔드 §5.7 실패 복구](../01_backend_plan.md), 검토 당시 611~615행

현재 설계는 저장 커밋 후 비동기 호출하고 재시도까지 실패해야 DB에 기록한다. 커밋 직후 또는 재시도 중 프로세스가 종료되면 실패 기록 자체가 없다. 예약 작업의 마지막 실행 시각도 webhook 처리와 어떤 순서로 확정하는지 불명확하다.

**권고:** 글 변경과 같은 트랜잭션에서 ‘처리 대기 캐시 갱신 이벤트’를 저장하고, 작업자가 성공할 때 완료 처리한다. 별도 메시지 서버 없이 PostgreSQL 테이블 하나로 처리할 수 있다.

### 3.5 [중간·M3] 작업본 편집 항목과 저장 모델의 불일치

**근거:** [프론트엔드 §7.3](../02_frontend_plan.md), 검토 당시 330행 / [백엔드 PostDraft 모델](../01_backend_plan.md), 검토 당시 209~223행

에디터는 slug·Featured·발행일시를 편집하지만 PostDraft 모델에는 이 필드들이 없다. Featured는 공개본 직접 수정 예외지만, slug와 예약 시각은 언제 반영되는지 불명확하다.

첫 작업본 생성 시 아직 작업본 `version`이 없는데 어떤 `expectedVersion`을 보내야 하는지도 필요하다.

**권고:** 필드별로 ‘작업본 저장 / 즉시 공개 반영 / 별도 액션’을 구분한다. 첫 생성·재저장·발행·폐기의 버전 규칙을 정의한다. 예약 글의 작업본을 발행할 때 기존 예약 시각을 유지하는지도 포함한다.

### 3.6 [중간·M3] slug 이력 충돌과 상세 응답의 버전 일관성

**근거:** [백엔드 PostSlugHistory 모델](../01_backend_plan.md), 검토 당시 225~230행 / [프론트엔드 상세 조회](../02_frontend_plan.md), 검토 당시 103행

PostSlugHistory의 `oldSlug`와 Post의 `slug`는 각각 고유하지만 두 테이블 전체에서의 충돌은 막지 못한다. A 글을 `hello → hello-new`로 바꾼 뒤 B 글이 `hello`를 사용하면 이전 링크가 어느 글을 가리켜야 하는지 모호해진다.

**권고:** 사용한 slug를 영구 예약할지, 재사용을 허용할지 정한다. 비공개·삭제 글의 이전 URL 처리도 정의한다.

상세 페이지의 메타·원문 병렬 조회는 발행 순간 서로 다른 버전을 받을 수 있다. 내부 렌더링 응답을 하나로 묶거나 버전 일치 검사 방식을 정하면 좋다.

### 3.7 [중간·M3~M4] 캐시 태그 의존성 누락

**근거:** [백엔드 §5.7 이벤트별 무효화 표](../01_backend_plan.md), 검토 당시 600~609행 / [프론트엔드 §4](../02_frontend_plan.md)

다음 연결이 빠져 있다.

- 태그 이름·slug 변경과 삭제 → 글의 태그 표시·필터 갱신
- 기술스택 수정 → 프로젝트 카드와 상세의 기술 정보 갱신
- 프로젝트 공개·삭제·slug 변경 → 사이트맵 갱신

사이트맵은 `posts` 태그로만 설명되어 있어 프로젝트 변경 시 갱신이 누락될 수 있다.

**권고:** API에서 반환하는 연관 데이터까지 기준으로 태그 의존성을 점검한다.

## 4. 사용성과 문서 정합성에서 남은 사항

### 4.1 연락처 복사 예외의 이벤트 규칙 충돌

**근거:** [접근 통제 §2.2](../04_access_control_and_content_protection.md), 검토 당시 149~153행

`copy`, `cut`, `contextmenu`에는 `.allow-select` 예외가 있지만 `selectstart`와 단축키 규칙은 여전히 입력 요소만 예외다. 그대로 구현하면 이메일 선택이나 `Cmd+C`가 막힐 수 있다.

**권고:** 연락처 예외를 관련 이벤트 전체에 일관되게 적용한다.

### 4.2 placeholder 대비 기준 설명 오류

**근거:** [UI §9](../../ui_design/ui_design_spec.md), 검토 당시 501행

‘입력값이 아니므로 대비 기준 대상이 아니다’는 설명은 잘못됐다. placeholder도 대비 기준 대상이며 `aria-label`을 추가해도 시각적 대비 요구는 남는다.

**권고:** placeholder 색상도 해당 배경에서 대비 기준을 충족하도록 정한다. [W3C 공식 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

### 4.3 M5 배포와 M6 통계의 의존성

운영 오픈을 M5로 옮겼지만 관리자 대시보드와 방문자 E2E에는 여전히 조회수·좋아요가 필수처럼 등장한다.

**권고:** M5에서는 해당 UI·테스트를 제외하거나 기능 활성화 조건을 명시한다. 개요의 ‘MVP’가 M5인지 M6까지인지도 통일한다.

### 4.4 MVP 스키마의 M7 모델 참조

**근거:** [백엔드 User 모델](../01_backend_plan.md), 검토 당시 105행

User에 `McpToken[]`이 있지만 McpToken은 M7 변경으로 정의된다. 단계별 스키마를 그대로 구현한다면 참조를 M7로 옮기거나 모델을 미리 포함해야 한다.

### 4.5 이전 설명과 표 구조 정리

- UI 상세는 `/projects`를 3열로 확정했지만 [UI IA와 반응형 표](../../ui_design/ui_design_spec.md)에는 2열 설명이 남아 있다. 검토 당시 63행, 218~219행이다.
- [개요](../00_overview.md)의 Q3·Q4가 남은 확인 사항이 아니라 변경 이력 표로 들어가 있다. 검토 당시 258~259행이다.

## 5. 권장 진행 판단

현재 상태에서 M0~M1은 시작할 수 있다.

- **M3 구현 전:** 작업본 계약, 캐시 갱신·복구 기준, slug 정책을 확정한다.
- **M4 구현 전:** 프로젝트·기술스택·사이트맵의 캐시 의존성을 정리한다.
- **M5 운영 오픈 전:** M6 기능의 UI·테스트 의존성을 제거하거나 활성화 조건을 명시한다.
- **M7 착수 전:** 비공개 미디어의 인증 캐시, 이미지 최적화, 공개 철회 범위를 다시 설계한다.
