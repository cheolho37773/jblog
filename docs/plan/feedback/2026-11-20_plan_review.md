# 블로그·포트폴리오 기획 검토 피드백

> 검토일: 2026-11-20
> 검토 범위: `docs/plan` 기획문서 5개, `docs/ui_design/ui_design_spec.md`, 주요 참고 이미지
> 이 문서는 기존 기획에 대한 피드백이다. 기존 기획문서는 수정하지 않았으며, 아래 제안은 확정된 요구사항을 대체하지 않는다.

## 1. 종합 의견

전체적으로 구현을 시작할 수 있을 만큼 구체적인 기획이다. 공개 사이트·관리자·AI 작성의 역할이 나뉘어 있고, API·데이터 모델·화면·마일스톤까지 연결되어 있다.

다만 콘텐츠를 안전하게 수정하고 공개하는 과정에는 빈틈이 있다. 디자인 세부값보다 편집 초안과 공개본의 경계, 응답별 캐시 정책, 발행·비공개 전환의 완료 기준을 먼저 확정하는 것이 좋다.

## 2. 잘 잡혀 있는 부분

- 블로그는 Markdown, 프로필·경력은 구조화된 폼으로 구분한 점이 적절하다.
- Next.js와 NestJS의 책임, OpenAPI를 통한 계약 관리가 명확하다.
- Redis·검색엔진·별도 스토리지 서버를 초기 범위에서 제외한 판단은 서비스 규모에 잘 맞는다.
- AI 결과를 초안으로 제한하고 사람이 검토한 뒤 발행하는 방향이 좋다.
- 두 디자인을 그대로 섞지 않고 공통 토큰으로 통일하려는 원칙이 있다.

## 3. 구현 전에 해결할 항목

아래 순서는 구현 전 검토 우선순위다. 실제 구현 결함을 확인한 결과가 아니라 기획에 명시된 동작과 누락된 규칙을 근거로 한 검토다.

### 3.1 발행 글 자동저장과 공개 본문 분리

**근거:** [프론트엔드 §7.3 자동저장](../02_frontend_plan.md#73-markdown-에디터-markdowneditor), [백엔드 §3.2 Post 모델](../01_backend_plan.md#32-prisma-스키마-초안)

자동저장은 30초마다 서버에 `PATCH`하고, Post 모델은 본문을 하나만 저장한다. 발행 글 편집 시 별도 규칙이 없어 작성 중인 문장이 저장되고 캐시 갱신 후 공개될 수 있다.

**권고:** 공개본과 편집 초안을 분리하고, ‘수정사항 발행’에서 공개본을 교체한다. 최소한 MVP에서는 발행 글의 자동저장을 로컬 복구용으로 제한한다. 여러 탭이나 AI와의 동시 수정에 대비해 `version` 또는 `updatedAt` 기반 충돌 검사도 정의한다.

### 3.2 Nginx API 라우팅과 Next.js webhook 경로 구분

**근거:** [개요 §3 시스템 아키텍처](../00_overview.md#3-시스템-아키텍처), [프론트엔드 §3 디렉터리 구조](../02_frontend_plan.md#3-디렉터리-구조)

Nginx는 `/api/*` 전체를 NestJS로 보내지만 Next.js에도 `/api/revalidate`가 있다. 현재 내부 webhook 주소는 web 컨테이너를 직접 가리켜 동작할 수 있으나, 외부 경로와 개발용 rewrite의 처리 규칙은 불명확하다.

**권고:** web 전용 내부 경로로 분리하거나 정확한 예외 라우팅을 명시한다. 로컬과 운영에서 각각 어느 서버가 요청을 받는지 확인 기준을 둔다.

### 3.3 응답별 HTTP 캐시 정책 구분

**근거:** [백엔드 §4.2 공개 API](../01_backend_plan.md#42-공개-api), [백엔드 §6 비기능 요구사항](../01_backend_plan.md#6-비기능-요구사항)

공개 GET 응답의 기본 정책은 `public, max-age=60`이지만, 반응 API의 `liked`는 방문자별 값이다. 이를 그대로 적용하면 다른 방문자의 좋아요 상태가 재사용될 수 있다.

같은 상세 URL이 내부 키 유무에 따라 `contentMd` 포함 여부를 바꾸는 점도 캐시 정책에 반영해야 한다.

**권고:** 공용 콘텐츠, 방문자별 상태, 관리자 데이터, 내부 원문 응답의 HTTP 캐시 정책을 구분한다. 방문자별 상태와 관리자 응답은 공유 캐시에서 제외한다. 내부 원문은 별도 엔드포인트로 분리하면 계약과 검증이 단순해진다. HTTP 캐시와 Next.js 서버의 데이터 캐시는 구분해 설계한다.

### 3.4 예약 발행의 노출 지연 기준 확정

**근거:** [개요 §5.2 글 작성 흐름](../00_overview.md#52-글-작성-흐름), [프론트엔드 §4 라우팅 및 렌더링](../02_frontend_plan.md#4-라우팅--렌더링-전략)

`revalidate: 300`만으로 예약 글의 ‘최대 5분 지연’을 보장하기 어렵다. 시간 만료는 정해진 시각의 백그라운드 실행을 의미하지 않으며, 요청 시점에 갱신되고 오래된 응답이 먼저 제공될 수 있다. 실제 동작은 채택할 Next.js 버전과 캐시 설정을 기준으로 확정해야 한다. [Next.js 공식 문서](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)

**권고:** 다음 중 하나를 선택한다.

- 예약 시각 이후 방문 요청에 따라 노출되며 지연을 허용한다.
- 일정 시간 내 노출을 보장하고, 주기 작업으로 대상 글을 찾아 캐시를 무효화한다.

개요의 `SCHEDULED` 상태와 실제 스키마의 `DRAFT/PUBLISHED`도 통일한다. 예약을 별도 상태로 둘지, 미래 `publishedAt`에서 계산할지 정한다.

### 3.5 캐시 무효화의 영향 범위와 실패 복구

**근거:** [백엔드 §5.1 글 저장 및 발행](../01_backend_plan.md#51-글-저장--발행)

현재 발행 로직은 `posts`, 해당 글 태그를 갱신하고 실패하면 로그만 남긴다. 글 하나의 발행·비공개 전환은 다른 글의 이전/다음·관련 글, 카테고리 수, RSS, 사이트맵에도 영향을 준다.

**권고:** 변경 이벤트별 무효화 대상 표를 만든다. 삭제·비공개 전환·slug 변경을 반드시 포함한다. webhook 실패에는 제한된 재시도와 실패 확인 수단을 두고, slug 변경 시 이전 URL의 리다이렉트 정책도 정한다.

### 3.6 초안 첨부파일의 공개 범위

**근거:** [개요 §3 이미지 서빙](../00_overview.md#3-시스템-아키텍처), [AI 작성 §3.2 이미지 도구](../03_ai_authoring_mcp_plan.md#32-tools)

업로드 파일은 Nginx가 직접 서빙하므로 초안에 올린 이미지도 URL을 알면 접근할 수 있다. AI 이미지 도구도 같은 파이프라인을 사용한다.

**권고:** ‘글의 비공개’와 ‘첨부파일의 비공개’를 별도로 정의한다. 초안 스크린샷에 비공개 정보가 들어갈 수 있다면 인증된 미리보기 경로나 발행 시 공개 전환이 필요하다. 미디어 삭제 시 사용 중인 글의 이미지가 깨지지 않도록 참조 확인 정책도 정한다.

### 3.7 모든 기기 로그아웃의 효력 범위

**근거:** [접근 통제 §1.3 로그인 흐름](../04_access_control_and_content_protection.md#13-로그인-흐름), [백엔드 §5.6 인증 상세](../01_backend_plan.md#56-인증-상세)

로그아웃은 refresh 토큰을 폐기한다. 이미 발급한 access JWT는 별도 세션 확인이 없다면 만료까지 유효할 수 있다.

**권고:** 즉시 차단이 요구사항인지, 최대 15분의 잔여 유효시간을 허용할지 정한다. 즉시 차단하려면 요청 시 세션 폐기 상태나 사용자 토큰 버전을 검사하는 설계가 필요하다.

### 3.8 조회 통계의 정의와 보관 구조

**근거:** [백엔드 §3.2 PostViewLog 모델](../01_backend_plan.md#32-prisma-스키마-초안), [백엔드 §5.2 조회수](../01_backend_plan.md#52-조회수-중복-방지)

조회 로그는 방문자 중복 판정용이며 30일 후 삭제된다. 누적 조회수는 Post에 남는다. 최근 30일 차트는 로그 보관 기간 안에서는 계산할 수 있지만, 로그 정리 경계나 글 삭제에 따라 통계의 의미가 달라질 수 있다.

**권고:** 일별 집계 데이터와 중복 판정 로그를 분리한다. 대시보드의 ‘조회수’가 중복 제거 조회인지 전체 페이지뷰인지 정의하고, 글 삭제 후 통계를 보존할지도 정한다.

## 4. 블로그·포트폴리오 목적에서의 보완

### 4.1 방문자와 주요 행동 정의

**근거:** [개요 §1 서비스 개요](../00_overview.md#1-서비스-개요)

현재 사용자 정의는 방문자와 관리자 구분에 집중한다. 채용 담당자는 역할·성과·연락처를, 동료 개발자는 문제 해결 과정과 코드를 확인하려 한다. 이 두 방문 흐름을 기준으로 홈과 프로젝트 상세의 우선순위를 정하면 좋다.

### 4.2 프로젝트 카드의 정보 보강

**근거:** [UI §6.3 Project Card](../../ui_design/ui_design_spec.md#63-project-card-m-project-card--19102-19103)

카드는 이미지와 이름 중심이다. 이름 아래에 해결한 문제 한 줄, 본인 역할, 핵심 기술을 보여주면 포트폴리오로서 효용이 커진다.

프로젝트 상세는 MCP 작성 가이드에 있는 개요·기술 선택·기여·트러블슈팅·성과 구조를 일반 작성에도 적용하는 것이 좋다.

### 4.3 홈에서 블로그로 진입하는 거리

**근거:** [UI §7.1 Home](../../ui_design/ui_design_spec.md#71-home-)

현재 순서는 Hero → 기술스택 → 프로젝트 → 큰 Featured Post → 최신 글이다. 참고 이미지처럼 여백과 이미지가 크면 모바일에서 글이 상당히 아래로 밀릴 수 있다.

**권고:** Hero에 ‘프로젝트 보기 / 기술 글 읽기’ 진입점을 두고, Featured 영역은 콘텐츠가 충분할 때 표시한다.

### 4.4 복사 방지와 포트폴리오 사용성

**근거:** [접근 통제 Part 2](../04_access_control_and_content_protection.md#part-2-읽기-페이지-콘텐츠-복사-방지-r2)

현재 범위는 경력·프로필·카드와 인쇄까지 모두 막는다. 채용 검토를 위한 저장, 부분 코드 복사, 번역·사전 사용에도 영향을 준다.

기술적 한계를 문서에 명시한 점은 좋다. 억제 장치로 유지하더라도 이메일·연락처·이력서와 포트폴리오 인쇄의 예외는 재검토할 만하다. 이는 확정된 요구사항 변경을 전제로 하지 않는 사용성 제안이다.

## 5. 문서 사이에서 맞춰야 할 사항

| 항목 | 현재 차이 | 필요한 결정 |
|---|---|---|
| 프로젝트 목록 | UI 기본 2열, FE 계획 3열 | 페이지별 기본 열 수 확정 |
| 이력서 PDF | 프로필에서 업로드하지만 미디어 API는 이미지만 허용 | PDF 업로드 또는 외부 URL 방식 |
| 태그 | API와 상세 배지는 있으나 공개 탐색 경로가 불명확 | `/blog?tag=` 등 연결 규칙 |
| 한글 본문 폰트 | UI는 Noto Serif KR, FE 로딩 목록에는 없음 | 실제 폰트·weight·로딩 범위 |
| 디자인 검수 | 화면을 재구성하면서 원본 대비 ±2px 요구 | 원본 컴포넌트와 조합된 페이지의 검수 기준 분리 |

### 접근성 대비 기준

[UI §9](../../ui_design/ui_design_spec.md#9-접근성--품질-기준)의 ‘메타 텍스트는 보조 정보라 낮은 대비를 유지한다’는 방침은 AA 준수 목표와 맞지 않는다. 날짜·작성자도 정보를 전달하는 텍스트이므로 보조 정보라는 이유만으로 예외가 되지는 않는다.

**권고:** 이 색상은 QA까지 미루지 말고 토큰 단계에서 정한다. [W3C 대비 기준](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html)

## 6. M7 AI 작성에서 보완할 사항

M7의 후순위 배치는 유지하되 다음 항목은 착수 전에 기획에 반영하는 것이 좋다.

### 6.1 원격 이미지 URL 가져오기

`upload_image(sourceUrl)`은 서버가 임의 URL에 접근하는 기능이다. 내부 주소 접근·리다이렉트·응답 크기 제한이 빠져 있다.

**권고:** 첫 버전은 파일 업로드만 지원해 범위를 줄이거나, 원격 URL 지원 시 목적지와 리다이렉트 검증·시간 제한·응답 크기 제한을 정의한다. [OWASP SSRF 대응 지침](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

### 6.2 토큰 발급자 연결과 사람의 편집 보호

[MCP 토큰 모델](../03_ai_authoring_mcp_plan.md#6-데이터-모델-변경)에 발급자 연결 필드가 없어 ‘발급자가 현재도 허용된 사용자인지 확인’하는 정책을 구현하기 어렵다.

또한 `source=AI_MCP`인 초안을 사람이 편집해도 현재 수정 조건을 계속 만족할 수 있다.

**권고:** 토큰과 발급 사용자의 관계를 저장한다. 사람이 편집한 초안에 AI가 다시 쓰기를 시도할 때의 허용 정책과 충돌 검사도 정의한다.

## 7. 권장 개발 순서

1. 공개 글·프로젝트 열람
2. 관리자 작성·검토·발행
3. 캐시·백업·배포
4. 통계와 편의 기능
5. MCP 기반 AI 초안 작성

초기 구현에서는 편집 중인 내용과 공개된 내용의 경계, 캐시 정책, 발행·비공개 전환의 완료 기준을 우선 확정한다.
