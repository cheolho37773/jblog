# 블로그·포트폴리오 기획 4차 검토 피드백

> 검토일: 2026-11-21
> 검토 범위: `docs/plan` 기획문서 6개와 `docs/ui_design/ui_design_spec.md`
> 이전 검토: [1차](./2026-11-20_plan_review.md), [2차](./2026-11-20_plan_review_02.md), [3차](./2026-11-21_plan_review_03.md), [에이전트 팀 가이드 검토](./2026-11-21_agent_team_guide_review.md)
> 이 문서는 구현 결함을 확인한 결과가 아니라 기획의 규칙을 조합했을 때 발생할 수 있는 문제를 검토한 결과다. 기존 기획문서와 이전 피드백은 수정하지 않았다.
> 근거 행 번호는 4차 검토 당시 문서 기준이며 이후 개정 시 달라질 수 있다.

## 1. 종합 의견

3차 피드백과 에이전트 팀 가이드 제안은 대부분 반영됐다. 이제 큰 구조를 바꾸기보다는 협업 절차를 시험하고 동시성·상태 전환의 빈틈을 보완하는 단계다.

현재는 **M0 시험 운영을 시작할 수 있는 수준**이다. 작은 PR 하나로 CI SHA 매핑·소유권 검사·검수 예외를 확인하는 것이 좋다. 콘텐츠 설계에서는 작업본의 고유 식별자와 refresh 동시성 처리를 M3 착수 전에 보완하는 것이 우선이다.

## 2. 반영이 잘 된 부분

- 작업별 실행 방식과 난도별 모델 배정이 추가됐다.
- 테스트 환경 준비와 테스트 설계의 책임이 분리됐다.
- 검수 기준이 `dev`로 통일되고 SHA 기반 승인이 도입됐다.
- 첫 작업본 생성 시 공개본 버전을 검사하도록 수정됐다.
- 예약 글과 첨부파일의 공개 여부 재계산 규칙이 추가됐다.
- 인증 방식별 가드·CSRF 적용과 입력 요소 복사 예외가 정리됐다.

## 3. 남은 주요 사항

### 3.1 [높음·M3] 작업본 폐기·재생성 시 버전 재사용에 따른 덮어쓰기

**근거:** [백엔드 PostDraft 모델 및 §5.1 버전 규칙](../01_backend_plan.md), 검토 당시 209~223행, 508~511행

PostDraft는 글 ID를 식별자로 사용하고 생성할 때마다 `version=1`로 시작한다.

다음 상황이 가능하다.

1. A 탭이 작업본 v1을 편집한다.
2. B 탭이 해당 작업본을 폐기하고 새 작업본을 만든다. 새 작업본도 v1이다.
3. A 탭의 늦은 자동저장이 `expectedVersion=1`로 도착한다.
4. 서버는 버전이 같으므로 새 작업본을 덮어쓸 수 있다.

**권고:** 작업본마다 UUID 같은 고유 식별자를 부여하고, 저장·발행·폐기 요청에서 **작업본 ID와 버전을 함께 검사**한다. 폐기 후 재생성 시 식별자가 달라져야 한다.

강제 발행 `force=true`도 확인창에서 사용자가 확인한 공개본 버전을 받아야 한다. 확인창을 연 뒤 공개본이 다시 바뀌었다면 재확인을 요구하는 편이 안전하다.

### 3.2 [중간·M0] CI 실행 SHA와 PR head SHA의 구분

**근거:** [협업 기획서 §6.5](../05_collaboration_architecture.md), 검토 당시 474~490행

현재 기획은 모든 결과를 같은 head SHA에 묶는다. 하지만 `pull_request` 워크플로는 기본적으로 PR head가 아닌 **대상 브랜치와 합친 테스트용 merge commit**을 검사한다. [GitHub 공식 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)

이 둘을 동일한 값으로 비교하면 정상적인 CI 결과를 불일치로 판단할 수 있다.

**권고:** 다음 정보를 구분해 기록한다.

- PR head SHA: 검수·G4 승인 대상
- 대상 `dev` SHA: 통합 기준
- CI가 실제 검사한 SHA: head 또는 테스트용 merge commit

CI 결과가 어떤 head와 base의 조합을 검증했는지 확인하면 된다.

### 3.3 [중간·M0] 충돌 없는 rebase의 재검수 생략 조건

**근거:** [협업 기획서 §6.5 재검수 예외](../05_collaboration_architecture.md), 검토 당시 489행

현재 규칙은 충돌 없는 rebase 후 변경분이 비어 있으면 검수를 생략한다. 하지만 텍스트 충돌 없이도 공유 함수·가드·DTO의 동작이 바뀔 수 있다. 작업 패치가 같아도 새 기반 코드와 조합한 결과는 달라질 수 있다.

**권고:** 재검수 생략 조건에 **기반 브랜치의 관련 계약·의존 코드 변경 여부**를 포함한다. 관련 변경이 없다면 CI만 다시 실행하고, 관련 변경이 있으면 영향 범위를 검수한다.

### 3.4 [중간·M0] PR 단위 소유권 검사와 여러 역할의 참여 관계

**근거:** [협업 기획서 §5.2](../05_collaboration_architecture.md), 검토 당시 284~312행

소유권 검사는 브랜치 접두어와 지시서의 쓰기 범위로 변경 파일을 검사한다. 하지만 하나의 BE 작업 PR에도 Test Agent의 테스트, Docs 기록, 검수 결과가 함께 들어간다.

브랜치 접두어를 엄격하게 적용하면 정상 변경이 차단되고, 전체 경로를 허용하면 구현 에이전트의 테스트 수정까지 허용할 수 있다.

**권고:** 두 검사의 목적을 나눈다.

- **도구·작업 단계 검사:** 현재 역할이 수정할 수 있는 파일인지 확인
- **PR 검사:** 승인된 참여 역할들의 변경 범위 합집합 안에 있는지 확인

생성 타입·잠금 파일·작업 기록의 허용 규칙도 이 기준에 포함한다.

### 3.5 [중간·M3] 여러 탭의 동시 refresh가 탈취로 오인될 가능성

**근거:** [프론트엔드 §7.1](../02_frontend_plan.md), 검토 당시 306~307행 / [백엔드 §5.6](../01_backend_plan.md), 검토 당시 609~610행

프론트엔드는 refresh Promise를 공유하지만 일반적인 메모리 Promise 공유는 같은 탭 안에서만 동작한다.

두 탭이 같은 refresh 쿠키로 동시에 요청하면 첫 요청이 토큰을 회전시킨 뒤 두 번째 요청은 폐기된 토큰 재사용으로 처리되어 **모든 세션이 종료될 수 있다**. 재사용 감지가 정상 사용자도 재인증하게 만들 수 있다는 특성은 OAuth 보안 문서에서도 설명한다. [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)

**권고:** 탭 간 갱신 조정과 서버의 원자적 회전 처리를 정의하고, 두 탭 동시 갱신·응답 유실 후 재시도를 테스트한다. 단순히 재사용 검사를 제거하는 방식은 피한다.

### 3.6 [중간·M3] 같은 트랜잭션과 동시성 보장의 구분

**근거:** [백엔드 §4.5 상세 조회](../01_backend_plan.md), 검토 당시 458행 및 §5.1 버전 규칙

상세 조회는 한 트랜잭션에서 읽으면 일관성이 보장된다고 설명한다. 하지만 PostgreSQL 기본 `Read Committed`에서는 같은 트랜잭션의 연속 조회도 서로 다른 시점의 데이터를 볼 수 있다. [PostgreSQL 17 공식 문서](https://www.postgresql.org/docs/17/transaction-iso.html)

**권고:** 핵심 보장마다 필요한 처리 방식을 명시한다.

- 버전 저장: 버전 조건을 포함한 원자적 갱신
- 작업본 생성·발행: 관련 행 잠금 또는 동등한 충돌 방지
- 상세 응답: 단일 조회 또는 일관된 스냅샷
- 미디어 공개 여부: 동시 참조 변경 시에도 결과가 맞도록 잠금·재시도 정의

구현 세부 전체를 기획에 적을 필요는 없지만 **충족해야 할 동시 실행 시나리오**는 테스트 기준으로 남겨야 한다.

### 3.7 [중간·M3] 과거 slug 복귀와 영구 리디렉션의 충돌

**근거:** [백엔드 §5.1 slug 정책](../01_backend_plan.md), 검토 당시 530~535행

이전 주소를 301로 이동시키면서 같은 글이 과거 slug로 돌아가는 것도 허용한다.

`A → B` 리디렉션을 캐시한 방문자에게 다시 `B → A`가 생기면 순환 이동이 발생할 수 있다.

**권고:** 영구 리디렉션을 유지한다면 과거 slug로의 복귀를 제한하는 편이 단순하다. 복귀를 허용하려면 리디렉션 캐시 정책과 왕복 변경 시나리오를 별도로 검증한다.

## 4. 작게 정리할 부분

| 항목 | 남은 불일치 |
|---|---|
| 단일 실행 | 협업 §4.0은 Test·Docs 생략을 허용하지만 §4.2와 완료 기준은 여전히 항상 수행하는 것으로 읽힌다. 조건부 적용 표시가 필요하다 |
| 테스트 환경 소유권 | DevOps가 앱별 Jest·Vitest 설정을 맡지만 파일 소유권 표에는 해당 경로의 예외가 없다 |
| 재시도 횟수 | outbox의 시도 횟수 증가와 배열 인덱스·5회 실패 종료 순서를 명확히 할 필요가 있다 |
| HTTP 캐시 지연 | `stale-while-revalidate=300`이 있으므로 ‘최대 60초 이전 데이터’라는 설명은 엄밀하지 않다 |
| AI 작성 표기 | 글별 표기 토글을 제공하지만 `showAiDisclosure`는 SiteSetting에만 있다. 글별 저장 필드가 필요하다 |

## 5. 권장 진행 순서

1. **M0 시험 운영:** 작은 PR 하나로 CI SHA 매핑, 소유권 검사, rebase·검수 기록 예외를 확인한다.
2. **M3 착수 전:** 작업본 고유 식별자, 강제 발행의 확인 버전, refresh 동시성 처리를 보완한다.
3. **M3 구현·검증:** 원자적 버전 검사와 읽기 일관성, slug 왕복 변경 시나리오를 검증한다.
4. **M7 전:** 미디어의 동시 참조 변경과 글별 AI 작성 표기의 저장 계약을 확정한다.
