# 에이전트 팀 예시 가이드 검토 및 반영 제안

> 검토일: 2026-11-21
> 검토 대상: 사용자가 제공한 「에이전트 팀 가이드」와 현재 [협업 아키텍처 기획서](../05_collaboration_architecture.md) v0.3
> 이 문서는 반영 제안이며 확정된 요구사항을 대체하지 않는다. 기존 기획문서와 이전 피드백은 수정하지 않았다.

## 1. 종합 의견

예시를 그대로 적용하기보다는 **팀 운영 비용을 줄이는 원칙을 가져오는 것**이 적절하다. 현재 협업 기획서는 계약·소유권·검수 절차가 이미 구체적이므로, 실행 방식 선택과 테스트 환경 책임을 보강하면 좋다.

우선 반영할 것은 다음 세 가지다.

1. 필요한 역할만 실행하는 기준
2. 테스트 환경 준비 책임
3. 작업 지시서의 실행 명령·계약 기준·필수 검증 항목

기존 협업 체계를 크게 바꾸지 않으면서 운영 비용을 줄일 수 있는 보완이다.

## 2. 추가하면 좋은 부분

| 예시의 항목 | jblog에 적용할 방식 |
|---|---|
| 팀 구성 전 필요성 판단 | 작업마다 단일 세션·서브에이전트·팀 중 실행 방식을 선택 |
| 크로스커팅 변경 주의 | 인증·DB·공유 계약 변경은 책임자 한 명이 순서를 통제하고 단계별 진행 |
| 역할별 모델 선택 | 단순 실행·기록과 설계·테스트 설계를 구분해 모델 배정 |
| QA 환경 설정 제한 | DevOps가 실행 환경을 준비하고 Test Agent는 테스트 설계·작성·검증에 집중 |
| 작업 크기 제한 | 파일 수보다 하나의 검증 가능한 결과를 기준으로 작업 분할 |
| 구체적인 완료 조건 | 성공 동작뿐 아니라 거부 조건·회귀 방지 조건까지 명시 |
| 최종 보고 전 완료 확인 | 필수 작업의 성공·실패·보류 상태를 확인하고 미완료를 보고 |

### 2.1 역할 정의와 실제 실행을 구분

현재 기획은 Backend·Frontend·Test·DevOps·Docs 역할을 정의하지만, 작은 작업에서도 이 흐름을 전부 거치는 것으로 읽힐 수 있다.

다음처럼 구분하면 좋다.

- **작은 수정:** 담당 세션 하나가 처리하고 기존 검사·검수를 적용한다.
- **독립 작업 2~3개:** 필요한 서브에이전트만 실행한다.
- **지속적인 조율이 필요한 작업:** 팀 방식을 검토한다.
- **공유 계약을 바꾸는 작업:** 책임자 한 명이 계약과 순서를 통제한다.

단일 세션으로 처리하더라도 CI·독립 검수·G4 승인 기준은 유지한다.

예시의 ‘20개 미만은 혼자’ 같은 숫자는 절대 기준으로 쓰지 않는 편이 좋다. 인증 파일 3개를 바꾸는 작업이 문구 파일 30개를 바꾸는 작업보다 복잡할 수 있다.

**반영 위치 제안:** 협업 기획서 §4 작업 흐름에 실행 방식 선택 기준을 추가한다.

### 2.2 크로스커팅 변경은 동시 변경을 통제

크로스커팅 변경을 주의하라는 취지는 유용하지만, DB·인증 변경을 항상 한 세션이 전부 구현해야 하는 것은 아니다.

jblog에는 이미 협업 기획서 §5.3의 공유 계약 우선 원칙이 있으므로 다음 흐름으로 보강하면 된다.

> 영향 분석 → 계약 확정 → 공통 변경 → 영역별 구현 → 통합 검증

핵심은 **계약이 바뀌는 도중에 FE·BE·테스트가 서로 다른 가정으로 병렬 구현하지 않도록 하는 것**이다. 공통 변경이 안정된 뒤 독립 영역의 작업을 나눌 수 있다.

**반영 위치 제안:** §4.4 병렬 실행 기준과 §5.3 공유 계약 우선 원칙에 단계별 진행 규칙을 추가한다.

### 2.3 테스트 환경 준비와 테스트 설계의 책임 분리

현재 DevOps는 CI와 로컬 환경을 담당하지만, Jest·Vitest·Playwright 설정과 테스트용 DB·서버의 생명주기 책임은 더 명확히 할 수 있다.

| 책임 | 담당 |
|---|---|
| 테스트 프레임워크·공통 설정·실행 명령 | DevOps |
| 앱의 테스트 부팅·의존성 주입 지원 | Backend / Frontend |
| 검증 시나리오·테스트·픽스처 작성 | Test Agent |
| 테스트용 DB·서버 시작·종료 | Testcontainers·Playwright 등의 실행 도구 |

**Test Agent를 명령 실행만 하는 역할로 축소하는 것은 권하지 않는다.** jblog는 테스트 선작성과 독립적인 완료 기준 검증을 중요하게 다루므로 이 역할은 유지해야 한다. 환경 장애가 나면 환경 담당자에게 넘기도록 한다.

**반영 위치 제안:** §3 역할 정의, §4.3 테스트 선작성 규칙, §11.5~§11.6 역할별 명세에 책임과 인계 규칙을 추가한다.

### 2.4 작업 지시서에 실행 정보 추가

현재 지시서의 목표·참조·쓰기 범위·완료 기준에 다음 항목을 추가하면 재탐색 비용을 줄일 수 있다.

```markdown
- 실행 방식: 단일 세션 / 서브에이전트 / 팀
- 선택 이유: 독립 작업 여부, 공유 계약 변경 여부
- 선행 준비: 필요한 서비스와 의존 작업
- 실행 명령: 해당 작업의 검사 명령
- 계약 기준: OpenAPI·스키마의 경로와 기준 커밋
- 필수 검증: 성공·실패·충돌 시나리오
- 인계 대상: 결과를 확인할 담당자
- 중간 보고 조건: 계약 변경, 환경 장애, 예상 범위 초과
```

API 응답 구조는 프롬프트마다 수동 복제하기보다 기존 OpenAPI와 생성 타입을 기준으로 삼는다. 예시가 필요하면 계약과 일치하는 예시를 연결한다.

**반영 위치 제안:** §9의 작업 지시서 형식을 확장한다.

### 2.5 작업 크기는 검증 가능한 결과 기준으로 분할

‘5~10개 파일’보다 **한 번에 검토하고 검증할 수 있는 결과 하나**를 기준으로 잡는 편이 좋다.

예를 들어 작업본 기능 전체를 한 작업으로 묶기보다 다음처럼 나눌 수 있다.

- 작업본 생성·저장
- 수정사항 발행·충돌 처리
- 에디터 연동

파일 수와 예상 시간은 보조 지표로 사용한다. 작업 분할로 생기는 계약·인계 비용도 함께 고려한다.

### 2.6 완료 기준과 최종 보고 구체화

‘모든 테스트 통과’만 적는 대신 작업의 핵심 결과를 명시한다. 예를 들어 작업본 생성이라면 성공 생성뿐 아니라 오래된 공개본 버전 거부와 기존 작업본 충돌도 완료 기준에 포함한다.

다만 작업별 필수 시나리오가 기존 필수 CI와 관련 회귀 검사를 대체해서는 안 된다.

최종 보고 전에는 해당 작업의 필수 참여자와 필수 검사가 완료됐는지 확인한다. 실패·보류·미완료가 있으면 이를 완료와 구분해 보고한다.

## 3. 그대로 적용하지 않는 편이 좋은 부분

| 예시의 규칙 | 검토 의견 |
|---|---|
| 파일 수로 실행 방식 고정 | 파일 수는 보조 지표다. 변경 위험·독립성·공유 계약·조율 필요성을 함께 본다 |
| 크로스커팅 변경은 항상 단일 세션 | 책임자를 단일화하고 공통 변경을 직렬화하되, 계약 안정 후 영역별 분할은 허용한다 |
| QA는 무조건 저비용 모델 | 테스트 실행과 인증·동시성 테스트 설계는 난도가 다르다. 역할명보다 작업의 판단 난도로 배정한다 |
| API 키를 프롬프트에 직접 제공 | 서비스·환경·스키마는 명시하되 비밀값은 환경변수나 비밀 저장소로 전달한다. 지시서에는 변수명과 주입 방법만 적는다 |
| 실제 외부 서비스만 사용 | jblog의 로컬 PostgreSQL·Testcontainers 방침을 유지한다. 개발·테스트·운영 환경을 명시하는 것으로 충분하다 |
| 에이전트 간 직접 메시지 필수 | 현재의 오케스트레이터 중심·파일 기반 전달을 유지해도 된다. 메시지를 쓰더라도 결정과 인계는 문서에 남긴다 |
| QA는 테스트 실행만 담당 | Test Agent의 테스트 설계·선작성·독립 검증 역할을 유지한다 |
| 핵심 테스트 3개만 통과하면 완료 | 작업별 필수 시나리오를 구체화하되 필수 CI와 관련 회귀 검사를 유지한다 |
| QA 토큰 62%, 메시지 비용 1x/Nx | 제시된 사례의 수치로 보고 jblog 운영 기준으로 일반화하지 않는다 |

## 4. 기존 방식을 유지할 부분

- **API 계약:** OpenAPI와 `packages/api-types`를 단일 기준으로 유지한다.
- **파일 소유권:** 기존 매트릭스와 worktree 격리, 변경 파일 검사를 유지한다.
- **정보 전달:** 오케스트레이터 중심·파일 기반 기록을 유지한다.
- **검증:** Test Agent의 테스트 선작성과 Codex 독립 검수를 유지한다.
- **승인:** 작업 규모와 실행 방식에 관계없이 기존 필수 승인·검수 기준을 적용한다.

## 5. 반영 우선순위

1. **우선 반영:** 필요한 역할만 실행하는 기준, 테스트 환경 준비 책임, 작업 지시서 확장
2. **함께 보강:** 크로스커팅 변경의 단계별 진행, 검증 가능한 결과 중심 작업 분할, 완료 상태 확인
3. **운영 후 조정:** 모델 배정과 작업 크기 기준은 실제 소요 시간·재작업·비용을 기록해 보정
