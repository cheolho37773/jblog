# 블로그·포트폴리오 기획 3차 검토 피드백

> 검토일: 2026-11-21
> 검토 범위: `docs/plan` 기획문서 6개와 `docs/ui_design/ui_design_spec.md`
> 이전 검토: [1차 피드백](./2026-11-20_plan_review.md), [2차 피드백](./2026-11-20_plan_review_02.md)
> 이 문서는 기획의 동작과 문서 간 정합성을 검토한 결과이며, 구현 코드에서 결함을 확인한 결과는 아니다. 기존 기획문서와 이전 피드백은 수정하지 않았다.
> 근거 행 번호는 3차 검토 당시 문서 기준이며 이후 개정 시 달라질 수 있다.

## 1. 종합 의견

2차 피드백의 주요 항목은 대부분 반영됐다. 이번 검토에서는 새로 추가된 협업 아키텍처와 수정된 설계를 실제 흐름에 적용했을 때의 빈틈을 중점적으로 확인했다.

현재 판단은 **M0 착수 가능, 협업 절차는 보완 후 시험 운영**이다. 검수 기준 브랜치와 SHA 규칙을 먼저 정리하고 M0의 작은 작업 하나로 전체 흐름을 시험하는 것이 좋다. M3 전에는 첫 작업본 생성의 버전 검사를, M7 전에는 예약 콘텐츠와 미디어의 공개 전이를 보완해야 한다.

## 2. 개선된 부분

- 캐시 갱신 outbox와 재시작 후 복구가 구체화됐다.
- 작업본의 필드별 반영 방식과 버전 규칙이 명확해졌다.
- slug 영구 예약과 상세 데이터 단일 응답이 반영됐다.
- 비공개 미디어의 인증 캐시 문제와 이미지 최적화 경로가 정리됐다.
- 배포 보류, MVP 범위, 통계 기능의 후속 일정이 구분됐다.

## 3. 구현 전에 해결할 사항

### 3.1 [높음·M0] 작업 기준 브랜치와 검수 기준 브랜치의 불일치

**근거:** [협업 기획서 §6.1](../05_collaboration_architecture.md), 검토 당시 318행

로컬 검수 대상을 `main` 대비 diff로 지정한다. 그러나 작업 브랜치는 `dev`에서 만들고 `main`에는 당분간 병합하지 않는다.

이대로면 작업이 쌓일수록 이번 작업뿐 아니라 이미 병합된 다른 작업까지 매번 검수하게 된다. PR diff와 로컬 검수 범위도 달라진다.

**권고:** 검수 기준을 PR 대상인 `dev`와의 merge-base로 통일하고, 검수 결과에 `base SHA`와 `head SHA`를 기록한다.

### 3.2 [높음·M0] 검수·승인이 유효한 커밋의 미정의

**근거:** [협업 기획서 §4.2](../05_collaboration_architecture.md), 검토 당시 162~165행

작업 흐름은 CI → Codex → Docs 기록 → Merge 순서다. 검수 이후 Docs 커밋, 수정, rebase가 발생했을 때 재검증 범위가 명시되어 있지 않다.

검수받은 코드와 실제 병합되는 코드가 달라질 수 있다. G4도 PR 번호만 승인하면 이후 추가된 커밋까지 승인한 것으로 취급될 여지가 있다.

**권고:** CI·검수·G4 승인에 대상 SHA를 연결하고, head 변경 시 필요한 재검사를 정의한다. 검수 결과 자체를 커밋할 때는 코드 변경과 구분한 예외 규칙을 둔다. GitHub도 새 변경으로 기존 승인이 오래된 상태가 되는 문제를 별도로 다룬다. [GitHub 공식 문서](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

### 3.3 [높음·M3] 첫 작업본 생성 시 오래된 공개본의 편집을 감지하지 못함

**근거:** [백엔드 §5.1 버전 규칙](../01_backend_plan.md), 검토 당시 508행

작업본 최초 생성은 `expectedVersion`을 생략하고 생성 시점의 `Post.version`을 `baseVersion`으로 기록한다.

다음 상황에서 문제가 생긴다.

1. A 탭이 공개본 v1을 연다.
2. B 탭에서 수정사항을 발행해 공개본이 v2가 되고 작업본은 삭제된다.
3. A 탭이 v1 내용을 기반으로 첫 자동저장을 한다.
4. 서버는 작업본이 없으므로 생성하고 `baseVersion=2`를 기록한다.

이후 A의 작업본은 버전 검사에 통과하면서 B의 수정사항을 되돌릴 수 있다.

**권고:** 첫 생성에도 클라이언트가 편집을 시작한 공개본 버전을 보내야 한다. 예를 들어 `expectedPostVersion`을 검사한 후 작업본을 생성한다.

### 3.4 [높음·M7] 예약 글의 미디어 공개 시점과 참조 해제 처리의 불명확성

**근거:** [AI 기획서 §4.3](../03_ai_authoring_mcp_plan.md), 검토 당시 151행 / [백엔드 §5.1 예약 발행](../01_backend_plan.md), 검토 당시 537행

미디어 공개 전환은 ‘발행’ 시 공개한다고 설명한다. 하지만 예약 글도 `status=PUBLISHED`다. 반면 예약 시각 도달 작업은 캐시 이벤트만 생성한다.

구현 해석에 따라 다음 문제가 생길 수 있다.

- 예약 등록 즉시 첨부파일이 먼저 공개된다.
- 예약 시각이 되어도 첨부파일은 비공개로 남는다.

공개 글에서 이미지를 제거하거나 교체했을 때, 더 이상 공개 참조가 없는 기존 미디어를 비공개로 되돌리는 규칙도 빠져 있다.

**권고:** 공개 여부를 `PUBLISHED && publishedAt <= now()`인 콘텐츠의 참조 기준으로 정의하고, 예약 도달·본문 교체·삭제·비공개 전환 때 함께 재계산한다.

### 3.5 [중간·M0] Write/Edit 훅만으로 파일 소유권을 강제할 수 없음

**근거:** [협업 기획서 §5.2](../05_collaboration_architecture.md), 검토 당시 215행

소유권 강제 방법은 `Write`와 `Edit` 경로를 검사한다. 하지만 Bash로 실행하는 스크립트·포매터·파일 생성도 저장소를 변경할 수 있다.

CI는 소유권 위반을 ‘경고’만 하므로 강제한다고 설명한 수준과 실제 차단 범위가 다르다. Claude Code 훅도 도구별로 구분된다. [공식 훅 문서](https://code.claude.com/docs/en/hooks)

**권고:** 목적을 실수 방지로 명시하고 작업 전후 변경 파일 검사와 CI 필수 검사를 추가한다. 강한 격리가 필요하면 파일시스템 권한까지 별도로 설계한다.

### 3.6 [중간·M0] 협업 절차와 파일 소유권의 내부 충돌

**근거:** [협업 기획서 §4.2, §4.3, §5.2, §5.4, §6.4](../05_collaboration_architecture.md)

| 항목 | 충돌 | 필요한 정리 |
|---|---|---|
| 검수 대응 기록 | `docs/reviews/**`는 Codex만 생성 가능하지만 `_response.md`는 오케스트레이터가 작성 | 결과와 대응 기록의 경로·권한 분리 |
| PR 생성 시점 | §4.2는 PR 생성 후 CI·검수, §5.4는 검수가 모두 끝난 뒤 PR 생성 | Draft PR → CI → 검수 → Ready 순서로 통일 |
| 테스트 파일 | 구현 에이전트 수정 금지와 내부 단위 테스트 작성 허용이 함께 존재 | 테스트 종류별 소유권 명시 |
| 잠금 파일 | `pnpm-lock.yaml` 담당이 없음 | 의존성 변경과 잠금 파일 갱신 담당 지정 |

특히 대응 기록은 소유권 표(검토 당시 212행)와 지적 처리 규칙(검토 당시 350행)이 직접 충돌한다.

### 3.7 [중간·M2~M7] 인증 방식별 글로벌 가드 예외의 명시 필요

**근거:** [백엔드 §5.6](../01_backend_plan.md), 검토 당시 605행

글로벌 `JwtAuthGuard`를 기본 적용하지만 다음 요청은 서로 다른 인증 수단을 사용한다.

- OAuth 시작·콜백: 기존 access JWT 없이 접근
- Refresh: 만료된 access JWT 대신 refresh 토큰 사용
- 내부 API: `X-Internal-Key`
- MCP: Bearer PAT

각 전용 가드를 추가하는 것만으로 글로벌 JWT 요구가 사라지는 것은 아니다.

**권고:** 경로별로 적용·생략되는 인증 가드와 CSRF 검사를 표로 확정한다. `@Public()`은 JWT 생략 용도인지 모든 인증 생략 용도인지도 구분한다.

### 3.8 [중간·M2] 입력 요소의 선택 방식을 고려하지 않은 복사 예외 판정

**근거:** [접근 통제 §2.2](../04_access_control_and_content_protection.md), 검토 당시 155행

복사 예외 판정은 복사·잘라내기 시 `window.getSelection()`의 시작·끝 노드를 검사하도록 한다.

입력 요소 내부의 선택은 일반 본문 선택과 동일하게 다루면 안 된다. 검색창에서는 이벤트 대상·포커스 요소와 `selectionStart/selectionEnd`를 기준으로 처리해야 한다. [MDN 입력 선택 API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/selectionStart)

**권고:** 입력 요소는 먼저 허용하고 일반 DOM 텍스트에만 `.allow-select` 선택 범위 검사를 적용한다.

## 4. 추가 정리 사항

### 4.1 검수 보고서 경로

[협업 기획서](../05_collaboration_architecture.md)는 `_workspace/` 체계를 폐기하지만, [UI 검수 보고서 경로](../../ui_design/ui_design_spec.md)는 여전히 `_workspace/06_review_report.md`다. 검토 당시 각각 494행, 532행이다.

**권고:** 협업 체계에 맞는 기록 경로로 통일한다.

### 4.2 배포 보류와 WBS

배포는 보류됐지만 [백엔드 BE-10 WBS](../01_backend_plan.md)에는 배포 스크립트·백업이 남아 있다. 검토 당시 768행이다.

**권고:** 현재 수행할 빌드·테스트 작업과 M-Deploy로 넘길 작업을 구분한다.

### 4.3 GitHub 요금제와 브랜치 보호

협업 기획서는 비공개 GitHub 저장소를 권장하면서 브랜치 보호를 필수로 둔다.

**권고:** M0에서 계정 요금제의 지원 여부를 확인한다. [GitHub 지원 범위](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

### 4.4 AI 프로젝트 썸네일의 필수 여부

[AI 프로젝트 생성 도구](../03_ai_authoring_mcp_plan.md)는 썸네일을 선택값으로 받지만 Project 모델의 `thumbnailUrl`은 필수다. 검토 당시 AI 기획서 81행, 백엔드 273행이다.

**권고:** 기본 이미지를 지정하거나 초안에서 null을 허용하는 정책이 필요하다.

## 5. 권장 진행 순서

1. **M0:** 검수 기준을 `dev`로 통일하고 SHA 기반 검수·승인 유효성, 파일 소유권과 PR 절차를 정리한다.
2. **M0 시험 운영:** 작은 작업 하나로 이슈 → 브랜치 → CI → 검수 → 승인 → Merge 흐름을 검증한다.
3. **M2 전:** 입력 요소 복사 예외와 인증 가드 적용 규칙을 확정한다.
4. **M3 전:** 첫 작업본 생성에도 공개본 버전 검사를 적용한다.
5. **M7 전:** 예약 콘텐츠와 미디어의 공개 전이, 공개 참조 해제 처리를 정의한다.
