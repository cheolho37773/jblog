## 1. 목적과 원칙

jblog는 개발자 1명이 **AI 에이전트 팀**과 함께 만든다. 이 문서는 누가 무엇을 하고, 작업이 어떤 순서로 흐르며, 어디서 사람이 승인하는지를 정한다.

| 원칙 | 의미 |
|---|---|
| **만드는 쪽과 검사하는 쪽을 분리** | 구현은 Claude Code 에이전트, 독립 검수는 다른 모델인 Codex가 맡는다. 같은 모델의 같은 맹점을 피하기 위해서다 (1·2차 기획 피드백이 실제 결함을 찾아낸 방식) |
| **기획 문서가 단일 기준** | `docs/plan/*`, `docs/ui_design/*`가 요구사항의 원본이다. 에이전트는 문서에 없는 결정을 스스로 내리지 않는다 |
| **사람이 최종 결정** | 계획 승인, 기획 변경, 의견 충돌, Merge는 개발자가 결정한다 (§7) |
| **변경 격리** | 작업마다 별도 브랜치·worktree에서 진행하고, 공유 파일은 담당자를 정해 충돌을 막는다 (§5) |
| **비싼 검사는 싼 검사 뒤에** | 자체 검사(로컬에서 CI와 같은 검사) → Codex 최종 검수 → push → CI → 개발자 순서. 테스트가 깨진 코드에 검수 비용을 쓰지 않고, 검수가 끝난 코드만 push한다 |

### 확정된 결정사항

| # | 항목 | 결정 |
|---|---|---|
| C1 | Codex 연결 | **로컬 Codex CLI(읽기 전용)만** 쓴다. GitHub PR Codex 리뷰는 연결하지 않는다 (2026-11-21 변경) |
| C2 | DevOps | **별도 DevOps Agent 유지** (구성도의 Backend Agent에서 인프라를 분리) |
| C3 | 개발자 승인 관문 | **작업 분할 계획(G1)**, **기획·결정사항 변경(G2)**, **Claude·Codex 의견 충돌(G3)**, **Merge(G4)** 4곳 모두 |
| C4 | 검수 순서 | 자체 검사(로컬에서 CI와 같은 검사) → **Codex 최종 검수** → **push** → CI → PR 요청 → 개발자 Merge. Codex 검수가 끝나기 전에는 push하지 않는다 (2026-11-21 변경) |
| C5 | 템플릿 반영 시점 | 이 문서 검토 통과 후 `.claude/` 수정 (M0 첫 작업) |
| C6 | 코드 가독성 | **가독성을 최우선 품질 기준**으로 둔다. 규칙은 §10-a, Codex 검수 관점에 포함 |
| C7 | 기본 브랜치 | **`dev`를 GitHub 기본(default) 브랜치**로 둔다. `main`은 릴리스용으로 남겨 두되 **`dev` → `main` Merge는 당분간 하지 않는다** |
| C8 | 작업 브랜치 | 작업 1개 = `dev`에서 만든 브랜치 1개. 작업과 검수가 모두 끝나면 **PR로 `dev`에 Merge** |
| C9 | 에러 수정 상한 | 모든 에러 수정 루프(자체 검사, CI, Codex 지적)는 **3회까지만** 에이전트가 시도하고, 그 이상은 **개발자 승인**이 있어야 계속한다 (§8) |
| C10 | 배포 | **보류** (인프라 미정, 개요 D6). DevOps Agent는 로컬 개발 환경과 CI까지만 맡는다 |
| C11 | GitHub 자동화 | 이슈 생성 → 브랜치 생성 → 작업·검수 → **브랜치 push**까지 오케스트레이터가 한다. PR 생성과 Merge는 개발자가 GitHub에서 직접 한다. 이슈는 PR의 `Closes #n`으로 자동 종료 (§5.6) |
| C17 | PR·Merge 담당 | **PR 생성과 Merge는 개발자가 GitHub에서 직접** 한다 (2026-11-21 변경). 오케스트레이터는 검수를 마친 브랜치를 push하고 브랜치 이름·head SHA·연결 이슈 번호와 검사 결과를 보고한다 (PR 생성 링크는 보내지 않는다, 2026-11-21 개발자 지시). **개발자의 Merge가 곧 G4 승인**이다 |
| C12 | 저장소 공개 범위 | **공개(Public) 저장소**. GitHub 무료 요금제에서 브랜치 보호를 쓰기 위해서이며, 코드가 포트폴리오 역할도 한다. 비밀정보는 저장소에 절대 두지 않는다 (§5.1-a) |
| C13 | 검수·승인의 유효 범위 | CI 결과·Codex 검수·G4 승인은 **특정 커밋(head SHA)에만 유효**하다. 이후 코드가 바뀌면 다시 확인한다 (§6.5) |
| C14 | 실행 방식 | 작업마다 **단일 실행**(담당 에이전트 1명) 또는 **서브에이전트 조합**(필요한 역할만) 중 선택한다. **팀 방식(에이전트 간 직접 메시지)은 보류**하고, M0 시험 운영 후 필요하면 G2로 도입한다 (§4.0) |
| C15 | 모델 배정 | **작업 난도 기준**. 기본: 오케스트레이터 Opus, 구현·테스트·DevOps Sonnet, Docs Haiku. 지시서에 "난도 높음"이 표시된 작업은 해당 구현·테스트 설계를 Opus로 올린다. 운영 기록으로 보정한다 (§4.0-b) |
| C16 | 테스트 환경 책임 | 테스트 **환경**(프레임워크 설정·실행 명령·CI)은 DevOps, 앱의 테스트 부팅 지원은 Backend/Frontend, 테스트 **설계·작성·검증**은 Test Agent (§4.3-a) |

## 2. 전체 구성도

구성도 원안에 **되돌아가는 화살표(피드백 루프)**, **승인 관문(G1~G4)**, **DevOps Agent**를 추가했다.

```
                         │ 개발자                        │  요구사항 · 목표 · 승인 기준

                                │               │ G1 계획 승인 / G2 기획 변경 / G3 충돌 판정 / G4 Merge

                │ Claude Code — 오케스트레이터 (메인 세션)              │
                │ 마일스톤 분해 · 작업 계획 · 계약 확정 · 배정 · 통합 · 보고 │
                └──┬──────────┬──────────┬──────────┬──────────┬───┘
                   ▼          ▼          ▼          ▼          ▼
              ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌──────────┐
              │Backend │ │Frontend│ │  Test  │ │ DevOps │ │   Docs   │   ← 서브에이전트
              │API·DB  │ │UI·UX   │ │테스트우선│ │CI/CD·인프라│ │변경 기록  │
              └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘ └────┬─────┘
                  └──────────┴────┬─────┴──────────┴───────────┘
                                  ▼
                ┌──────────────────────────────────────────┐
                │ Git: dev에서 작업별 브랜치 + worktree (로컬)  │
                │ ① 자체 검사 (CI와 같은 검사) + 범위 + 기록   │◀──────────┐
```

## 3. 역할 정의

### 3.1 역할 요약

| 역할 | 실체 | 핵심 책임 | 쓰기 권한 (요약, 상세는 §5.2) |
|---|---|---|---|
| **개발자** | 사람 | 요구사항·승인 기준 정의, G1~G4 결정 | 전체 |
| **오케스트레이터** | Claude Code 메인 세션 | 마일스톤 분해, 작업 계획서, 공유 계약 확정, 에이전트 배정, 결과 통합, 피드백 루프 관리, 보고 | `docs/work/**`, 공유 계약 파일(§5.3) |
| **Backend Agent** | 서브에이전트 `backend-dev` | NestJS API, Prisma 스키마·마이그레이션, 인증, 비즈니스 로직 | `backend/**` |
| **Frontend Agent** | 서브에이전트 `frontend-dev` | Next.js 공개 사이트·관리자, 디자인 토큰, 컴포넌트, 디자인 검수 수정 | `frontend/**`, `frontend/src/lib/markdown/**` |
| **Test Agent** | 서브에이전트 `test-engineer` | 기획 문서 기준 테스트 **설계·선작성**, 완료 기준의 독립 검증, E2E·시각 회귀, 테스트 결과 보고. 환경 장애는 DevOps로 인계 | `**/*.spec.ts(x)`, `{frontend,backend}/test/**`, `frontend/e2e/**`, 테스트 픽스처 |
| **DevOps Agent** | 서브에이전트 `devops-engineer` | 모노레포·도구 설정, **테스트 프레임워크 공통 설정·실행 명령**, 로컬 개발 환경(Docker Compose), GitHub Actions CI, Dockerfile 빌드 검증, GitHub 자동화 설정. **배포는 보류(C10)** | `infra/**`, `.github/**`, 루트 설정 파일 |
| **Docs Agent** | 서브에이전트 `docs-writer` | 변경 이력, 구현 결과 기록, API 문서 동기화, 작업 인계 문서 | `docs/work/**`의 기록 파일, 각 기획 문서의 **변경 이력 섹션만** |
| **Codex 검수자** | Codex CLI / GitHub Codex 리뷰 | 버그·보안·설계 준수·회귀 위험 검수 | **없음 (읽기 전용)**. 검수 결과 파일만 생성 |

> 템플릿의 `architect`는 별도 에이전트로 두지 않는다. 설계는 이미 기획 문서로 확정되어 있고, 이후 설계 판단(작업 분해, 계약 확정)은 오케스트레이터가 맡는다. 설계 변경은 G2를 거친다.

### 3.2 오케스트레이터 (Claude Code 메인 세션)

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| 계획 | 마일스톤의 WBS 항목(BE-xx, FE-xx, SEC-xx, AI-xx)을 작업 단위로 분해하고 의존 관계·담당·완료 기준을 정한다 | `docs/work/<M>/plan.md` → **G1** |
| 계약 | 여러 에이전트가 공유하는 계약(Prisma 스키마, OpenAPI, 디자인 토큰)을 먼저 확정한다 (§5.3) | 계약 PR |
| 배정 | 작업마다 브랜치·worktree를 만들고 서브에이전트에게 작업 지시서를 준다 | `docs/work/<M>/tasks/<ID>.md` |
| 통합 | 결과를 받아 자체 검사 통과 여부를 확인하고 PR을 연다 | PR |
| 루프 관리 | CI 실패·Codex 지적을 해당 에이전트에게 되돌리고 횟수를 센다 (§8) | PR 코멘트 |
| 보고 | 개발자에게 결정이 필요한 것만 요약해서 올린다 | 대화 / PR 설명 |

**하지 않는 것**: 기획 문서의 결정사항(D1~D21, C1~C5)을 승인 없이 변경, 서브에이전트 대신 대량 구현 (작업 배정이 원칙. 단, 설정 한 줄 수정 같은 사소한 작업은 직접 처리 가능), Codex 검수 결과 파일 수정.

### 3.3 서브에이전트 공통 규칙

1. 작업 시작 전에 작업 지시서와 지시서가 가리키는 기획 문서 섹션을 **반드시 읽는다**.
2. **쓰기 권한 밖의 파일은 수정하지 않는다.** 필요하면 작업 결과에 "변경 요청"으로 적어 오케스트레이터에게 넘긴다.
3. 기획 문서와 다르게 구현해야 할 이유가 생기면 구현을 멈추고 "기획 변경 제안"을 올린다 (→ G2).
4. 작업 완료 시 **인계 노트**(무엇을 바꿨나, 남은 일, 확인한 테스트)를 지시서 파일 하단에 기록한다.
5. 테스트를 약하게 만들어 통과시키지 않는다. 테스트가 틀렸다고 판단되면 Test Agent에게 수정을 요청한다 (§4.3).
6. 코드는 **가독성 규칙(§10-a)** 을 따른다. 동작하는 코드보다 읽히는 코드가 우선이며, 리팩터링이 필요하면 같은 작업 안에서 정리한다.
7. **민감 정보는 하드코딩하지 않고 `.env`로만 주입한다** ([개요 §6-b](./00_overview.md#6-b-민감-정보-관리-규칙-필수)). 새 환경변수가 필요하면 지시서에 변수명만 적고 `.env.example` 갱신을 요청한다.
8. 같은 에러를 고치는 시도는 **3회까지**다. 3회 안에 해결되지 않으면 멈추고 시도 내역을 정리해 오케스트레이터에게 넘긴다 (§8).

### 3.4 Codex 검수자

| 항목 | 규칙 |
|---|---|
| 권한 | 읽기 전용. 코드·문서를 수정하지 않는다 |
| 독립성 | Claude의 작업 과정·자기 평가를 입력으로 받지 않는다. **산출물(diff, 문서)만** 본다 |
| 기준 | 해당 작업의 기획 문서 섹션, 작업 지시서의 완료 기준, `AGENTS.md`의 검수 지침, **가독성 규칙(§10-a)** |
| 관점 | 버그 · 보안 · 설계 준수 · 회귀 위험 · **가독성** (가독성 지적은 보통 "낮음~중간", 이해를 막을 정도면 "중간") · **민감 정보 하드코딩** (발견 시 항상 "높음") |
| 출력 | 심각도(높음/중간/낮음) + 근거 위치(파일:행) + 권고 + 종합 판정(통과/수정 후 통과/재작업). 1·2차 기획 피드백 문서와 같은 형식 |
| 수정 금지 | 오케스트레이터와 서브에이전트는 검수 결과 파일을 수정하지 않는다. 대응은 별도 대응 기록에 남긴다 (§6.4) |

## 4. 작업 흐름

### 4.0 실행 방식 선택

역할을 정의했다고 해서 작업마다 모든 역할을 실행하지 않는다. **필요한 역할만 실행**하고, 실행 방식과 관계없이 **CI · Codex 검수 · G4는 항상 적용**한다.

| 실행 방식 | 언제 | 실행하는 역할 |
|---|---|---|
| **단일 실행** | 설정 몇 줄, 문구, 단순 버그처럼 한 영역 안에서 끝나고 새 완료 기준 테스트가 필요 없는 수정 | 해당 영역의 담당 에이전트 1명. 소유권 규칙은 그대로 |
| 단일 실행 + 재발 방지 테스트 | 버그 수정 | Test Agent가 **재현 테스트만 먼저** 짧게 작성 → 담당 에이전트가 수정 |
| **서브에이전트 조합** | 기능 작업 (독립 작업 2~3개, 완료 기준 테스트 필요) | Test Agent + 해당 구현 에이전트 (+ 필요 시 Docs). 영역이 하나면 구현 에이전트도 하나 |
| **공유 계약 변경** | 스키마·OpenAPI·디자인 토큰·인증 방식처럼 여러 영역이 같은 가정을 공유하는 변경 | **계약 책임자 1명**이 순서를 통제하는 단계별 진행 (§5.3-a) |
| ~~팀 방식~~ | (보류, C14) | — |

**판단 기준** — 파일 수는 보조 지표일 뿐이다. 인증 파일 3개가 문구 파일 30개보다 위험할 수 있다.

| 질문 | "예"이면 |
|---|---|
| 공유 계약(스키마·OpenAPI·토큰·인증 흐름)을 바꾸는가? | 공유 계약 변경 방식 |
| 새 동작이 생겨 완료 기준 테스트가 필요한가? | 서브에이전트 조합 (Test Agent 포함) |
| 두 영역 이상(BE·FE 등)에 걸치는가? | 영역별로 작업을 나눈다 (§4.0-a) |
| 위 셋 모두 "아니오"인가? | 단일 실행 |

오케스트레이터는 선택한 방식과 이유를 지시서에 적고(§9), G1 계획에서 개발자가 확인한다.

### 4.0-a 작업 크기: 검증 가능한 결과 하나

작업은 **한 번에 검토하고 검증할 수 있는 결과 하나**를 기준으로 나눈다. 파일 수·예상 시간은 보조 지표다. 나누는 만큼 계약·인계 비용이 생기므로 너무 잘게 쪼개지도 않는다.

예: "작업본 기능"(BE-05)을 한 작업으로 두지 않고
1. 작업본 생성·저장 (`PUT .../draft`, 최초 생성 버전 검사)
2. 수정사항 발행·폐기·충돌 처리
3. 에디터 연동 (FE)

### 4.0-b 모델 배정 (C15)

### 4.1 마일스톤 단위 흐름

```
[개발자] 마일스톤 시작 지시 (예: "M2 시작")
  → [오케스트레이터] docs/work/M2/plan.md 작성: 작업 목록 · 의존 관계 · 담당 · 완료 기준
  → (선택) Codex 로컬 검수: 계획서가 기획 문서를 빠짐없이 덮는지
  → G1 개발자 승인
  → 계약 작업(있으면) 먼저 → Merge
  → 작업들 병렬 진행 (§4.2)
  → 마일스톤 완료 점검: 개요 §7 완료 기준 · 착수 조건 표 확인
  → [Docs] 마일스톤 결과 기록 → 개발자 보고
```

### 4.2 작업(Task) 단위 흐름

아래는 **서브에이전트 조합** 기준의 전체 흐름이다. **[조건부]** 단계는 실행 방식(§4.0)에 따라 생략할 수 있고, 생략 여부와 이유는 지시서에 적는다. 표시가 없는 단계는 어떤 실행 방식에서도 생략하지 않는다.

| 단계 | 주체 | 내용 | 다음 단계 조건 |
|---|---|---|---|
| 1. 지시서·이슈 | 오케스트레이터 | `docs/work/<M>/tasks/<ID>.md` 작성(목표, 참조 문서 섹션, 쓰기 범위, 완료 기준, 의존 작업) + **GitHub 이슈 생성** (§5.6) | 의존 작업이 `dev`에 Merge 완료 |
| 2. 브랜치 | 오케스트레이터 | 이슈에 연결된 브랜치 `feat/<ID>-<요약>`을 **`dev`에서** 생성 + worktree | |
| 3. 테스트 선작성 **[조건부]** | Test Agent | 기획 문서의 테스트 항목·완료 기준을 **실패하는 테스트**로 작성하고 커밋. 단일 실행에서 새 완료 기준 테스트가 없으면 생략, 버그 수정은 재현 테스트만 | 테스트가 "의도대로 실패"함을 확인 |
| 4. 구현 | 담당 에이전트 | 테스트를 통과시키는 구현 | |
| 5. 자체 검사 | 담당 에이전트 | **CI와 같은 검사를 로컬에서**: lint · typecheck · test(Testcontainers 포함) · build + **변경 파일 범위 검사**(`git diff --name-only <merge-base>`가 쓰기 범위 안인지, §5.2). M0 이후 `pnpm verify` 한 명령으로 실행 | 전부 통과 |
| 6. 기록 **[조건부]** | Docs Agent (단일 실행이면 담당 에이전트가 인계 노트로 대신) | 변경 기록, 필요 시 기획 문서 변경 이력. **검수 전에** 커밋해서 검수 대상에 포함시킨다 | |
| 7. Codex 검수 | Codex | 자체 검사를 통과한 로컬 **head SHA**를 대상으로 로컬 CLI 검수 (§6). 지적 → 4로 돌아가 수정 후 재검수. 대응 기록 커밋은 검수 기록만이라 재검수 없음 (§6.5) | **push 허용 조건** (§6.4-a): 가장 최근 검수가 push할 head SHA를 대상으로 했고, 높음 0건이며, 중간 지적은 모두 "수정 후 재검수" 또는 "후속 처리 Issue" 또는 "G3에서 받아들여진 반박"으로 처리됨. 지적 수정은 3회 상한 / 반박 → G3 |
| 8. push | 오케스트레이터 | **Codex 최종 검수가 끝난 뒤에만** 작업 브랜치를 push (`git push -u origin <브랜치>`). push 이벤트로 CI가 실행된다 | Codex 최종 통과 |
| 9. CI | GitHub Actions | lint · typecheck · unit · integration(Testcontainers) · build · (해당 시) E2E · **소유권 검사·잠금 파일 검사(필수)** | 통과. 실패 → 4로 수정 → **Codex 재검수** → 다시 push (3회 상한, §8) |
| 10. PR 요청 | 오케스트레이터 → 개발자 | **브랜치 이름**, **head SHA**, **연결 이슈 번호**(PR 본문에 `Closes #<이슈>`, §5.6), 완료 기준·필수 검증 상태·검수 판정·에러 수정 횟수·후속 처리 목록을 보고 | |
| 11. PR · Merge | **개발자** | GitHub에서 PR 생성 → PR CI 확인 → **PR의 최신 커밋이 보고받은 head SHA와 같은지 확인** → `dev`에 squash merge (= **G4**). 수정이 필요하면 오케스트레이터에게 알리고, 수정·재검수 후 새 SHA를 다시 보고받는다 | 검수·CI가 그 SHA에 유효 (§6.5) |
| 12. 정리 | 오케스트레이터 | Merge 후 `git fetch`, worktree·로컬 브랜치 삭제. 이슈는 `Closes #n`으로 자동 종료(원격 브랜치는 자동 삭제) | |

### 4.3 테스트 선작성 규칙

- Test Agent는 **구현을 보기 전에** 기획 문서(각 문서의 "테스트" 섹션, 완료 기준, API 명세)를 기준으로 테스트를 쓴다. 구현에 맞춰 테스트를 쓰면 구현의 실수를 그대로 확인해 주는 테스트가 되기 때문이다.
- 구현 에이전트는 테스트 파일을 수정할 수 없다 (쓰기 범위 밖). 테스트가 기획과 다르거나 구현 불가능하면 Test Agent에게 수정을 요청하고, 기획 해석이 갈리면 오케스트레이터가 기획 문서로 판정한다. 그래도 갈리면 G2.
- 테스트 소유권은 **파일 이름 규칙**으로 나눈다.

  | 종류 | 파일 규칙 | 소유 |
  |---|---|---|
  | 완료 기준 검증 테스트 (API 통합, 계약, 컴포넌트 동작, E2E, 시각 회귀) | `*.spec.ts(x)`, `{frontend,backend}/test/**`, `frontend/e2e/**` | **Test Agent** |
  | 내부 구현 세부 단위 테스트 (헬퍼·유틸 함수) | 구현 파일 옆 `*.unit.test.ts(x)` | 구현 에이전트 |
  | 테스트 픽스처·팩토리 | `{frontend,backend}/test/fixtures/**` | Test Agent (구현 에이전트는 변경 요청) |

  구현 에이전트는 `*.spec.ts(x)`를 수정할 수 없고, `*.unit.test.ts(x)`로 완료 기준을 대신 검증할 수도 없다.
- 디자인 검수(UI 기획서 §11): Test Agent가 Playwright 스크린샷·컴포넌트 비교를 실행하고 차이 목록을 보고한다. 수정은 Frontend Agent가 한다.

### 4.3-a 테스트 환경 책임 (C16)

| 책임 | 담당 |
|---|---|
| 테스트 프레임워크 공통 설정 (Jest·Vitest·Playwright 설정 파일, 공통 실행 명령 `pnpm test:*`, CI 잡) | DevOps |
| 앱의 테스트 부팅 지원 (Nest 테스트 모듈 구성, 의존성 주입 대체 지점, Next 테스트 렌더 헬퍼, MSW 핸들러 기반) | Backend / Frontend |
| 검증 시나리오·테스트·픽스처 작성, 완료 기준의 독립 검증 | **Test Agent** |
| 테스트용 DB·서버의 시작·종료 | 실행 도구가 자동 관리 (Testcontainers, Playwright `webServer`) |

- Test Agent는 **명령 실행 담당으로 축소하지 않는다.** 테스트 선작성과 독립 검증이 이 역할의 핵심이다.
- 테스트가 **환경 문제**(컨테이너 기동 실패, 설정 누락, 포트 충돌)로 실패하면 Test Agent는 원인을 정리해 오케스트레이터에게 넘기고, DevOps(공통 설정) 또는 해당 앱 에이전트(부팅 지원)가 고친다. 환경 문제 수정도 3회 상한(§8)을 따른다.

### 4.4 병렬 실행 기준

| 병렬 가능 | 병렬 불가 (순서 필요) |
|---|---|
| 서로 다른 앱의 작업 (예: BE-03 공개 조회 API ↔ FE-03 Navbar/Footer) | 공유 계약 변경 → 그 계약을 쓰는 작업 |
| 같은 앱이라도 파일이 겹치지 않는 작업 | 같은 Prisma 모델을 바꾸는 두 작업 |
| 프론트엔드: 계약(OpenAPI 타입)이 확정된 뒤 MSW 모킹으로 백엔드와 병렬 | 마이그레이션 순서가 있는 작업 |
| 크로스커팅 변경의 ④ 영역별 구현 단계 | 크로스커팅 변경의 ①~③ 단계 (§5.3-a) |

동시에 진행하는 구현 작업은 **최대 3개**로 제한한다 (개발자가 G4에서 검토할 수 있는 양 기준).

## 5. Git · 저장소 운영

### 5.1 선행 조건 (M0 첫 작업)

현재 프로젝트 폴더는 **git 저장소가 아니다.** 협업 체계를 쓰려면 다음이 먼저 필요하다.

1. `git init`, `.gitignore`(node_modules, .env, .next, dist, 업로드 폴더 등)
2. GitHub 원격 저장소 **공개(Public)** (C12). 첫 커밋으로 `main` 생성 후 `main`에서 **`dev` 브랜치를 만들고 GitHub 기본 브랜치를 `dev`로 변경**
3. 브랜치 보호 (§5.4-a). 공개 저장소라 무료 요금제에서 사용 가능
4. 저장소 설정: Merge 방식은 **squash만 허용**, "Merge 후 브랜치 자동 삭제" 켜기, **Secret scanning + Push protection 켜기** (§5.1-a)
5. 이슈 라벨·템플릿 (§5.6). (GitHub Codex PR 리뷰는 연결하지 않는다, C1)
6. `AGENTS.md`(Codex 검수 지침), `CLAUDE.md`, `.claude/` 개편 (§11)

### 5.1-a 공개 저장소 운영 규칙

공개 저장소이므로 저장소에 올라간 것은 **누구나 볼 수 있다**고 가정한다.

| 항목 | 규칙 |
|---|---|
| 비밀정보 | `.env*`(`.env.example` 제외)는 `.gitignore`. 시크릿·토큰·OAuth client secret은 로컬 `.env`와 GitHub Actions Secrets에만 둔다 |
| 차단 장치 | GitHub **Secret scanning + Push protection**(공개 저장소 무료)으로 비밀정보가 포함된 push를 막는다. 로컬에서도 pre-commit 훅으로 비밀정보 패턴 검사(03 §4.2의 시크릿 스캐너 규칙 재사용) |
| 유출 시 | 커밋을 지우는 것으로는 부족하다 (이미 복제됐을 수 있음). **해당 비밀정보를 즉시 폐기·교체**한 뒤 이력 정리 |
| 콘텐츠 | 블로그 글·포트폴리오 데이터는 DB에 있으므로 저장소에 노출되지 않는다. 시드 데이터는 더미 텍스트만 쓴다 |
| 기획·검수 문서 | `docs/`는 공개된다. 개인정보(전화번호, 실제 이메일 외 연락처, 회사 내부 정보)를 쓰지 않는다 |
| 외부 기여 | 외부 PR은 받지 않는다 (README에 명시). 외부 PR의 CI는 시크릿에 접근하지 않도록 `pull_request` 이벤트만 사용 |
| Actions | 워크플로의 `permissions`를 최소로 지정 (기본 `contents: read`) |

### 5.2 파일 소유권 매트릭스

| 경로 | 쓰기 담당 | 다른 역할 |
|---|---|---|
| `backend/src/**` | Backend | 읽기 |
| `backend/prisma/schema.prisma`, `migrations/**` | **Backend (계약 작업으로만)** | 읽기 |
| `frontend/**` (테스트 제외) | Frontend | 읽기 |
| `frontend/src/lib/markdown/**` | Frontend | 읽기 |
| `backend/openapi.json` | **Backend (계약 작업으로만)**. Swagger 데코레이터에서 생성, 수동 수정 금지 | 읽기 |
| `frontend/src/generated/**` | **생성물** (생성 스크립트가 `backend/openapi.json`에서 생성, 수동 수정 금지) | 읽기 |
| `**/*.spec.ts(x)`, `{frontend,backend}/test/**`, `frontend/e2e/**` | Test | 읽기 |
| `**/*.unit.test.ts(x)` | 해당 앱의 구현 에이전트 | 읽기 |

| `pnpm-lock.yaml` | **`package.json`을 바꾼 쪽이 같은 커밋에서 `pnpm install`로 갱신**. 수동 편집 금지. 충돌 시 rebase 후 `pnpm install`로 재생성 | 읽기 |
| `infra/**`, `.github/**`, `turbo.json`, `pnpm-workspace.yaml`, 루트 `package.json`, 루트 도구 설정(`eslint.config.mjs`, `tsconfig.base.json`, Prettier, commitlint, `.husky/**`) | DevOps | 변경 요청 |

| `frontend/src/generated/**` 재생성 결과 | 생성 스크립트 (계약 변경 PR에서만 diff 허용) | 읽기 |
| `docs/plan/*.md` 본문 | **개발자 승인(G2) 후 오케스트레이터** | 읽기 |
| `docs/plan/*.md`의 "변경 이력" 섹션, `docs/work/**` 기록 | Docs (지시서는 오케스트레이터) | 읽기 |

**강제 방법과 한계**: 소유권 장치의 목적은 **에이전트의 실수 방지**다. 악의적 우회까지 막는 격리는 개발자 1인 프로젝트에 과하다고 보고 하지 않는다.

| 장치 | 막는 범위 | 한계 |
|---|---|---|
| Claude Code PreToolUse 훅 (`scripts/hooks/check-ownership.py`, 규칙 `scripts/ownership/roles.json`) | 에이전트의 `Write`/`Edit` 도구 호출 중 범위 밖 경로 | Bash로 실행한 스크립트·포매터·코드 생성기가 바꾸는 파일은 막지 못한다 |
| 자체 검사의 변경 파일 대조 (§4.2 5단계) | 작업 브랜치에서 실제로 바뀐 모든 파일 (`git diff --name-only <merge-base>`) | 커밋 전 검사라 에이전트가 건너뛰면 무력 |
| **CI 필수 검사 `ownership-check`** | PR 전체 변경을 **참여 역할들의 쓰기 범위 합집합**과 대조 (아래), `package.json` 없는 `pnpm-lock.yaml` 변경, 계약 PR이 아닌데 `backend/openapi.json`·`frontend/src/generated/**` 변경 검출. **실패하면 Merge 불가** | 지시서 경로 표기가 틀리면 오탐 → 지시서 수정 |

**검사 단위를 둘로 나눈다.** 하나의 BE 작업 PR에도 Test Agent의 테스트, Docs 기록, 검수 결과가 함께 들어가기 때문이다.

| 검사 | 질문 | 기준 |
|---|---|---|
| **역할 단위** (훅, 자체 검사) | 지금 실행 중인 **이 역할**이 이 파일을 바꿔도 되는가? | §5.2 매트릭스의 해당 역할 범위. 예: backend-dev가 `*.spec.ts`를 바꾸면 차단 |
| **PR 단위** (CI `ownership-check`) | PR 전체 변경이 **승인된 참여 역할들의 범위 합집합** 안에 있는가? | 지시서의 "실행 방식·참여 역할·쓰기 범위" (CI가 지시서 파일을 읽음) + 공통 허용 경로 |

- **공통 허용 경로** (참여 역할과 무관하게 PR에 포함 가능): 이 작업의 `docs/work/<M>/tasks/<ID>.md`, **이 작업 ID의 검수 기록** — `docs/reviews/<ID>/**`와 기획 문서 검수 결과 `docs/plan/feedback/<날짜>_<ID>.md`·`<날짜>_<ID>_r<N>.md` (§6.5와 같은 기준, 새 파일 추가만 허용·기존 파일 수정 불가), `package.json`과 짝을 이룬 `pnpm-lock.yaml`. 규칙 원본은 `scripts/ownership/roles.json`의 `pr_common_allow.regex`(날짜 `YYYY-MM-DD`·작업 ID·회차 `r<N>`을 정확히 대조하는 정규식), 판정은 `scripts/ownership/pr_common_allow.py`(자체 테스트 `--self-test`)
- **조건부 허용**: `backend/openapi.json`은 `contract/` 브랜치에서만(Backend 참여 시), 테스트 설정 파일은 DevOps가 참여 역할일 때만
- **계약 생성물**: `frontend/src/generated/**`는 어떤 역할도 손으로 고칠 수 없다(역할 단위 deny). 대신 PR 단위 검사에서는 **`contract/` 브랜치이고 생성 결과 일치 검사(`pnpm gen:api-types --check`)가 통과한 경우에만** 참여 역할과 무관하게 허용하고, 다른 브랜치에서 바뀌면 실패한다. 규칙 원본은 `roles.json`의 `pr_contract_generated`
- 역할별 커밋 구분은 커밋 trailer로 한다 (`Agent: backend-dev`). PR 단위 검사는 합집합만 보고, 역할을 넘은 수정은 역할 단위 검사와 Codex 검수가 잡는다

**Codex 결과 파일 보호**: `*.codex.md`는 생성 커밋 이후 내용이 바뀌면 CI `ownership-check`가 실패한다 (파일 해시를 대응 기록 첫 줄에 기록해 대조).

### 5.3 공유 계약 우선 원칙

| 계약 | 담당 | 계약 작업으로 처리하는 경우 |
|---|---|---|
| Prisma 스키마 + 마이그레이션 | Backend | 모델·필드 추가/변경. 마이그레이션은 Merge 순서대로 하나씩 |
| OpenAPI (Swagger 데코레이터 → `backend/openapi.json` → 프론트엔드 생성 타입 `frontend/src/generated/**`) | Backend | 엔드포인트·DTO 추가/변경. 계약 PR에는 컨트롤러 시그니처와 DTO만 두고, 구현은 빈 메서드(`501`)여도 된다 |
| 디자인 토큰 (`globals.css` 토큰, 타이포 유틸) | Frontend | 토큰 추가/변경 (M1에서 일괄 확정) |
| 환경변수 목록 (`.env.example`) | DevOps | 신규 변수 |

계약 PR이 Merge되면 그 계약을 쓰는 작업들이 병렬로 시작한다. 프론트엔드는 생성 타입과 MSW 모킹으로 백엔드 구현을 기다리지 않는다.

### 5.3-a 크로스커팅 변경의 단계별 진행

인증·DB·공유 계약처럼 여러 영역에 걸치는 변경은 **계약 책임자 1명**(보통 Backend, 디자인 토큰은 Frontend)이 순서를 통제한다. 한 세션이 전부 구현할 필요는 없지만, **계약이 바뀌는 도중에 FE·BE·테스트가 서로 다른 가정으로 병렬 구현하는 일은 없어야 한다.**

```
① 영향 분석 (오케스트레이터 + 계약 책임자): 바뀌는 계약, 영향받는 영역·테스트 목록
② 계약 확정 (contract/ 브랜치): 스키마·DTO·OpenAPI·토큰만. 동작 구현 없음 → 자체 검사 → Codex 최종 검수 → push·CI → 개발자 Merge
③ 공통 변경 (계약 책임자): 여러 영역이 공유하는 기반 코드 (예: 인증 가드, 공용 타입·유틸) → dev Merge
④ 영역별 구현 (병렬 허용): ②③이 Merge된 dev에서 FE·BE·Test 작업 분기
⑤ 통합 검증 (Test Agent): 영역을 가로지르는 E2E·계약 테스트
```

- ②③이 Merge되기 전에는 ④를 시작하지 않는다. 시작 후 계약 변경이 필요해지면 ④를 멈추고 ②로 돌아간다 (중간 보고 조건, §9).
- 지시서에는 기준이 된 계약의 **경로와 커밋 SHA**를 적는다 (§9 "계약 기준").

### 5.4 브랜치 · worktree · 커밋

**브랜치 모델**

```
main ─────●──────────────────────────────────────────  (릴리스용. 당분간 Merge 하지 않음)
           \
dev  (기본) ●───────●───────────●───────────●──────────  ← 모든 작업 PR의 대상
                    ↑ squash    ↑ squash    ↑ squash
feat/BE-03-...  ────┘           │           │
contract/BE-05a-...  ───────────┘           │
feat/FE-05-...  ────────────────────────────┘
```

| 항목 | 규칙 |
|---|---|
| 기본 브랜치 | **`dev`**. 새 작업 브랜치는 항상 최신 `dev`에서 만든다 |
| `main` | 릴리스 시점을 위한 브랜치로 남겨 둔다. **`dev` → `main` Merge는 하지 않는다** (배포 보류, C7·C10). 재개 조건과 절차는 배포 결정 시 정한다 |
| 작업 브랜치 | 작업(이슈) 1개 = 브랜치 1개. `contract/<ID>-<요약>`, `feat/<ID>-<요약>`, `fix/<ID>-<요약>`, `chore/<요약>`, `docs/<요약>` (`<ID>` = WBS ID) |
| PR | **Codex 최종 검수 → push → CI → PR 요청 → 개발자가 PR 생성·Merge** 순서다. 오케스트레이터는 PR을 만들지 않고, 검수를 마친 브랜치와 head SHA만 보고한다 (C17) |
| worktree 위치 | 저장소 밖 `../jblog-worktrees/<브랜치>` (Claude Code 서브에이전트의 worktree 격리 기능을 쓰면 그 기본 위치) |
| 커밋 | Conventional Commits (`feat(api): ...`, commitlint로 검사). 커밋 본문에 WBS ID |
| 동기화 | 작업 브랜치는 `dev`에 rebase. 공유 계약이 바뀌면 오케스트레이터가 영향 받는 브랜치에 rebase 지시 |
| Merge | `dev`로 squash merge만. Merge 후 브랜치 자동 삭제, worktree 정리 |

### 5.4-a 브랜치 보호

| 브랜치 | 규칙 |
|---|---|
| `dev` | PR 필수, 필수 상태 검사(CI 각 잡 + `ownership-check`) 통과, 직접 push 금지, force push·삭제 금지, 브랜치가 최신 `dev` 기준일 것 |
| `main` | 직접 push 금지, force push·삭제 금지. PR Merge도 개발자만 (당분간 사용 안 함) |

> **승인 리뷰 필수(Required approvals) 규칙은 켜지 않는다.** 개발자 본인이 PR을 만들고 Merge하므로, 자기 PR을 승인할 수 없는 GitHub 규칙 때문에 Merge가 막히기 때문이다. **G4 승인 = 개발자가 GitHub에서 Merge 버튼을 누르는 것**이다 (C17).

### 5.6 GitHub 이슈 기반 자동화

이슈 생성부터 브랜치 push까지는 오케스트레이터가 `gh` CLI로 처리하고, **PR 생성과 Merge는 개발자가 GitHub에서 직접** 한다 (C17).

| 단계 | 방법 | 자동화 주체 |
|---|---|---|
| ① 이슈 생성 | G1 승인된 계획의 작업마다 `gh issue create` (제목 `[BE-05] Post 작업본 · 수정사항 발행`, 라벨 `M3`·`BE`·`type:feat`, 본문에 지시서 링크·완료 기준) | 오케스트레이터 |
| ② 브랜치 생성 | `gh issue develop <이슈번호> --base dev --name feat/BE-05-post-draft` → 이슈에 브랜치가 연결된다. 이어서 `git worktree add` | 오케스트레이터 |
| ③ 작업 | §4.2의 3~6단계 | 서브에이전트 |
| ④ Codex 최종 검수 | 자체 검사 통과 후 `scripts/codex-review.sh <ID>` → 대응 기록 커밋 (push 전) | 오케스트레이터 · Codex |
| ④-a push · CI | push 허용 조건(§6.4-a)을 만족한 뒤 `git push -u origin <브랜치>` → push 이벤트로 CI 실행 | 오케스트레이터 · GitHub Actions |
| ④-b PR 요청 | 브랜치 이름, head SHA, 연결 이슈 번호, 검사·검수 결과를 보고 (PR 생성 링크는 보내지 않음) | 오케스트레이터 |
| ⑤ PR 생성 · Merge | GitHub에서 PR 생성(템플릿 작성, 본문에 `Closes #<이슈번호>`) → PR CI 확인 → PR 최신 커밋 = 보고받은 head SHA 확인 → **Squash and merge** | **개발자** |
| ⑥ 이슈 종료 | PR 본문의 `Closes #n` 키워드로 **Merge 시 GitHub가 자동 종료** | GitHub |
| ⑦ 정리 | 원격 브랜치는 저장소 설정으로 자동 삭제, 로컬 worktree는 `git worktree remove` | GitHub · 오케스트레이터 |

- **이슈 자동 종료의 조건**: `Closes #n`은 PR이 **기본 브랜치**에 Merge될 때 동작한다. 이 프로젝트는 기본 브랜치가 `dev`(C7)이므로 `dev`에 Merge되는 순간 이슈가 닫힌다. (기본 브랜치가 `main`이었다면 `main`에 들어갈 때까지 열려 있었을 것이다.)
- **진행 상태 표시 (선택)**: GitHub Projects 보드를 쓰면 기본 제공 워크플로로 "이슈 생성 → Todo", "PR 연결 → In Progress", "이슈 종료 → Done" 이동이 자동으로 된다.
- **추가 자동화 (선택)**: GitHub Actions로 PR 제목의 WBS ID 형식 검사, 브랜치 접두어와 변경 파일 범위 대조(§5.2), 라벨 자동 부여를 넣을 수 있다.
- **이슈가 열려 있으면**: PR 본문에 `Closes #n`이 빠져 Merge 후에도 이슈가 열려 있으면, 오케스트레이터가 정리 단계에서 확인해 개발자에게 알린다.
- **Merge 전 SHA 확인**: GitHub 화면의 Merge 버튼은 특정 커밋을 지정할 수 없으므로, PR의 Commits 탭에서 마지막 커밋이 보고받은 head SHA와 같은지 눈으로 확인한다. 다르면 Merge하지 말고 오케스트레이터에게 알린다.

## 6. Codex 독립 검수

### 6.1 로컬 검수 (단일 단계)

| 단계 | 시점 | 도구 | 대상 | 산출물 |
|---|---|---|---|---|
| **로컬 검수** | 자체 검사 통과 후, **push 전** / 기획 문서 변경 시 | Codex CLI 비대화형 실행, **읽기 전용 샌드박스** | **`dev`와의 merge-base 대비 head까지의 diff** (`git diff $(git merge-base origin/dev HEAD)..HEAD`) + 지시서 + 참조 기획 섹션 | `docs/reviews/<ID>/r<N>.codex.md` (첫 줄에 base·head SHA) |

- **기준 브랜치를 `dev`로 둔 이유**: PR 대상이 `dev`이고 `main`에는 Merge하지 않으므로, `main` 기준으로 비교하면 이미 Merge된 다른 작업까지 매번 다시 검수하게 된다. merge-base 기준이면 개발자가 만들 PR의 diff와 검수 범위가 같아진다.
- **GitHub PR Codex 리뷰를 쓰지 않는 이유 (C1)**: 로컬 검수가 기획 문서와 대조하는 최종 검수이고, 검수가 끝난 코드만 push하므로 PR 단계의 두 번째 검수는 두지 않는다.

- 로컬 검수는 기획 준수·설계 정합성처럼 **문서와 대조해야 하는 검수**와 diff의 라인 단위 버그를 함께 본다.
- 기획 문서만 바뀌는 변경(G2 이후 반영)은 ①만 수행하고 결과를 `docs/plan/feedback/`에 둔다.

### 6.2 로컬 검수 실행 (`scripts/codex-review.sh`)

```bash
# 사용: scripts/codex-review.sh <task-id>
# 1) diff·지시서·참조 기획 섹션을 하나의 입력으로 모은다
# 2) Codex CLI를 읽기 전용 샌드박스, 비대화형으로 실행한다
# 3) 결과를 docs/reviews/<task-id>/r<N>.codex.md 에 저장한다 (회차 N 증가)
#    첫 줄: base SHA(merge-base) · head SHA · 검수 일시
```
- Codex는 저장소 루트의 `AGENTS.md`를 지침으로 읽는다. 여기에 검수 기준·출력 형식·금지 사항(코드 수정 금지)을 둔다.
- CLI 명령 옵션(비대화형 실행, 샌드박스 지정)은 도입 시점의 Codex CLI 문서로 확정한다.
- 이 스크립트는 오케스트레이터가 실행할 수 있지만 **결과 파일은 수정하지 않는다** (§5.2 훅으로 차단).

### 6.3 (삭제) PR 리뷰 연결

GitHub PR Codex 리뷰는 사용하지 않는다 (C1, 2026-11-21).

### 6.4 지적 처리

| 심각도 | 처리 |
|---|---|
| **높음** | 반드시 수정. 반박하려면 G3 |
| **중간** | 수정 또는 "후속 처리"(GitHub Issue 생성 + 대응 기록에 링크). 후속 처리는 개발자가 G4에서 확인 |
| **낮음** | 담당 에이전트 판단. 대응 기록에 남김 |

- 지적마다 대응 상태를 **대응 기록**(`docs/reviews/<ID>/r<N>.response.md`, 오케스트레이터 작성)에 남긴다: `수정함(커밋)` / `후속 처리(Issue)` / `반박(근거)`. Codex 결과 파일(`r<N>.codex.md`)은 건드리지 않는다.
- 반박이 있으면 오케스트레이터가 근거를 정리해 **G3**로 올린다. 개발자가 결정할 때까지 해당 PR은 Merge하지 않는다.
- 수정 후 재검수는 같은 명령으로 다시 한다 (회차 `r2`, `r3`).

### 6.4-a push 허용 조건

Codex의 종합 판정 문구("통과 / 수정 후 통과 / 재작업")만으로 판단하지 않고, 아래를 **모두** 만족할 때 push한다. 절차(§4.2), 완료 기준(§10), PR 템플릿, 스킬이 같은 조건을 쓴다.

1. 가장 최근 검수 회차가 **push할 head SHA**를 대상으로 했다. 예외는 둘뿐이다: ① 그 뒤 추가된 커밋이 **검수 기록 파일만** 바꾼 경우(§6.5의 검수 기록 정의) ② 그 뒤 **rebase만** 했고 §6.5 "rebase 후 재검수 판단"에서 재검수 생략으로 판정해, 이전·이후 head SHA와 판단 근거를 대응 기록에 남긴 경우
2. 그 회차의 **높음 0건**
3. 그 회차의 **중간 지적은 모두** 다음 중 하나로 대응 기록에 남아 있다: 수정 후 재검수에서 해소됨 / 후속 처리 Issue 생성 / G3에서 개발자가 받아들인 반박
4. 낮음은 대응 기록에 남기기만 하면 된다

수정을 하면 코드가 바뀌므로 1번에 따라 재검수가 필요하다. 즉 "수정 후 통과" 판정을 받고 수정했다면 재검수를 받아야 push할 수 있고, 수정하지 않고 후속 Issue로 넘긴 경우에만 그 회차로 push할 수 있다.

### 6.5 검수·승인의 유효 범위 (SHA 기준)

검수받은 코드와 Merge되는 코드가 같다는 것을 보장하기 위해, 모든 확인 결과를 **head SHA**에 묶는다 (C13).

여기서 SHA는 세 가지를 구분한다.

| 이름 | 의미 | 쓰임 |
|---|---|---|
| **head SHA** | PR 브랜치의 최신 커밋 | **검수·G4 승인의 대상** |
| **base SHA** | 대상 브랜치 `dev`의 커밋 (merge-base 또는 CI 시점의 `dev` 끝) | 통합 기준 |
| **CI 검사 SHA** | CI가 실제로 checkout한 커밋. `pull_request` 이벤트는 기본적으로 head와 `dev`를 합친 **테스트용 merge commit**을 검사한다 | CI 결과의 근거 |

CI 검사 SHA는 head SHA와 **값이 다른 것이 정상**이다. 그래서 두 값을 직접 비교하지 않고, "CI가 어떤 head와 어떤 base의 조합을 검사했는가"로 확인한다. CI 잡은 시작 시 `head SHA`(`github.event.pull_request.head.sha`), `base SHA`(`github.event.pull_request.base.sha`), `검사 SHA`(`github.sha`)를 요약에 출력한다.

| 확인 | 유효 대상 | 기록 위치 |
|---|---|---|
| CI | **head SHA + base SHA 조합** (검사 SHA는 그 merge commit) | GitHub 상태 검사 + CI 요약의 SHA 3종 |
| Codex 로컬 검수 | `r<N>.codex.md` 첫 줄의 head SHA | 검수 파일 |
| G4 승인 | 개발자가 Merge한 PR의 head SHA (= 오케스트레이터가 보고한 SHA여야 함) | GitHub Merge 기록 |

**검수 이후 커밋이 추가됐을 때**

| 추가된 커밋의 내용 | 다시 해야 할 것 |
|---|---|
| **검수 기록만** — 이 작업 ID의 검수 결과·대응 기록: `docs/reviews/<ID>/**`, 그리고 기획 문서 검수(`--plan`)인 경우 그 결과 파일 `docs/plan/feedback/<날짜>_<ID>.md`·`<날짜>_<ID>_r<N>.md` | 없음 (예외). Codex 재검수는 하지 않는다. 다른 기획 문서나 다른 작업 ID의 피드백 파일은 예외가 아니다. `ownership-check`가 "검수 SHA 이후 변경 파일이 이 작업 ID의 검수 기록 경로뿐"인지 확인한다 |
| 코드·테스트·설정·기획 문서 변경 (수정, 리팩터링, Docs 기록 추가, **push 후 CI 실패 수정** 포함) | Codex **재검수 `r<N+1>`** 후 push (CI 재실행). push 전에 재검수를 마친다. 재검수 범위는 직전 검수 SHA 이후 변경분이 중심이며, 회귀 확인을 위해 전체 diff도 함께 준다 |
| `dev` 위로 rebase만 함 | CI 재실행은 항상. 재검수 여부는 아래 "rebase 후 재검수 판단" |
| PR 요청 이후 무엇이든 | 오케스트레이터가 새 head SHA와 재검사 결과를 **다시 보고**한다. 개발자는 PR 최신 커밋이 새로 보고받은 SHA와 같을 때만 Merge한다 |

**rebase 후 재검수 판단** — 텍스트 충돌이 없어도, 새 기반 코드와 조합하면 동작이 달라질 수 있다.

| 조건 | 재검수 |
|---|---|
| 충돌을 손으로 해결함 | 필요 (전체) |
| 작업 패치 자체는 같지만, 직전 검수 이후 `dev`에 들어온 변경 중 **이 작업의 관련 범위**가 있음 — 공유 계약(스키마·OpenAPI·토큰), 이 작업이 import하는 모듈, 인증 가드·공용 유틸 | 필요 (**영향 범위 검수**: 새로 들어온 관련 변경과 이 작업의 접점만) |
| 위 둘 다 아님 (관련 없는 영역의 변경만 `dev`에 들어옴) | 생략. CI 통과만 확인. 대응 기록에 **이전 head SHA → 새 head SHA, 새로 들어온 `dev` 변경 파일 목록, 관련 없다고 본 근거**를 남긴다 (§6.4-a 1-②의 근거) |

- "관련 범위"는 지시서의 "계약 기준"과 쓰기 범위의 import 그래프로 판단한다. 오케스트레이터가 `git diff <이전 base>..<새 base> --name-only` 결과를 이 기준과 대조해 PR에 기록한다.

- 이 순서 때문에 Docs 기록은 검수 **전에** 커밋한다 (§4.2 6단계). 검수 후 기록을 추가하면 재검수가 필요해진다.

**자동 상향 (개발자에게 바로 올리는 경우)**
- 에러 수정이 3회 안에 해결되지 않을 때 — **개발자 승인 없이 4회차를 시도하지 않는다** (§8)
- 보안 관련 "높음" 지적이 반박될 때
- 공유 계약(스키마·OpenAPI·토큰)의 **파괴적 변경**이 필요할 때
- 서브에이전트가 같은 작업에서 2회 연속 실패할 때

## 8. 피드백 루프와 상한

**원칙 (C9): 에러 수정은 3회까지만 에이전트가 시도한다. 그 이상은 개발자 승인이 필요하다.**

| 루프 | 되돌아가는 곳 | 상한 | 상한 초과 시 |
|---|---|---|---|
| 자체 검사 실패 (lint · typecheck · test) | 담당 에이전트 | **3회** | 작업 중단 → 개발자 승인 요청 |
| CI 실패 | 담당 에이전트 | **3회** | 작업 중단 → 개발자 승인 요청 |
| Codex 지적 (높음/중간) 수정 | 담당 에이전트 | **3회** (재검수 `r2`~`r4`까지) | 작업 중단 → 개발자 승인 요청 |
| 테스트-구현 해석 충돌 | 오케스트레이터 판정 | 1회 | G2 |

- **횟수 세는 법**: 같은 루프 안에서 "수정 → 재확인"을 1회로 센다. 원인이 다른 새 에러라도 같은 루프면 합산한다 (예: CI에서 서로 다른 실패 3건을 차례로 고쳤으면 3회).
- **상한 도달 시 보고 형식** (오케스트레이터 → 개발자):
  ```
  [승인 요청] BE-05 · CI 실패 3회
  - 시도 1: <에러 요약> → <수정 내용> → <결과>
  - 시도 2: ...
  - 시도 3: ...
  - 추정 원인: ...
  - 제안: ① 추가 시도 n회 허용 ② 지시서·범위 수정 ③ 기획 변경(G2) ④ 작업 보류
  ```
- 개발자가 추가 시도를 허용하면 허용한 횟수만큼 다시 시도하고, 그 횟수도 다 쓰면 다시 승인을 요청한다.
- 각 루프의 횟수는 PR의 "에러 수정 이력"과 대응 기록에 남는다.

## 9. 정보 전달 방식

템플릿의 "에이전트끼리 메시지로 직접 소통"하는 방식 대신, **오케스트레이터를 중심으로 파일을 통해 전달**한다 (팀 방식은 보류, C14). 모든 결정과 인계가 저장소에 남아 추적할 수 있고, Codex가 같은 자료로 검수할 수 있기 때문이다.

| 정보 | 위치 | 작성 |
|---|---|---|
| 요구사항·설계 (단일 기준) | `docs/plan/*`, `docs/ui_design/*` | 개발자 승인(G2) |
| **전체 진행 체크리스트** | `docs/work/00_master_checklist.md` (작업 PR의 기록 단계에서 자기 항목 체크 → Merge되면 반영) | 오케스트레이터 · docs-writer |
| 마일스톤 계획 | `docs/work/<M>/plan.md` | 오케스트레이터 |
| 작업 지시서 + 인계 노트 | `docs/work/<M>/tasks/<ID>.md` | 오케스트레이터(지시) / 담당 에이전트(인계) |
| 기획 변경 제안 | `docs/work/<M>/proposals/<번호>.md` | 오케스트레이터 → G2 |
| 검수 결과 / 대응 기록 | `docs/reviews/<ID>/r<N>.codex.md` / `r<N>.response.md` | Codex / 오케스트레이터 |
| 마일스톤 결과 | `docs/work/<M>/report.md` | Docs |
| 작업 추적 | GitHub Issues (라벨: `M2`, `BE`, `FE` 등, 제목에 WBS ID) ↔ PR 연결 | 오케스트레이터 |

**작업 지시서 형식**

```markdown
# BE-05-1 Post 작업본 생성·저장
- 마일스톤: M3 · 이슈: #34 · 브랜치: feat/BE-05-1-post-draft-save
- 실행 방식: 서브에이전트 조합 (test-engineer → backend-dev)
- 선택 이유: 새 동작(완료 기준 테스트 필요), 공유 계약 변경 없음(계약은 BE-05a에서 확정), 단일 영역
- 난도·모델: 높음(버전 규칙·동시성) → backend-dev·test-engineer 모두 Opus
- 의존 / 선행 준비: contract/BE-05a Merge 완료 · 로컬 PostgreSQL(Docker Compose) · 테스트 DB는 Testcontainers 자동
- 계약 기준: backend/prisma/schema.prisma, backend/openapi.json @ `<dev SHA>`
  (API 응답 구조는 이 OpenAPI와 그 생성 타입 `frontend/src/generated/**`를 기준으로 하고 지시서에 복제하지 않는다)
- 참조: 01_backend_plan.md §5.1 (필드별 반영 규칙, 버전 규칙)
- 쓰기 범위: backend/src/modules/posts/** (backend-dev), backend/test/posts/** (test-engineer)
- 실행 명령: pnpm --filter backend lint && pnpm --filter backend typecheck && pnpm --filter backend test -- posts
- 필수 검증 (완료 기준):
  - 성공: [ ] 작업본 최초 생성(`expectedPostVersion` 일치) [ ] 재저장 시 version+1

  - 회귀: [ ] 작업본 저장이 공개 응답·캐시 이벤트를 만들지 않음
  - 위 시나리오는 필수 CI·관련 회귀 테스트를 **대체하지 않는다**
- 비밀값: 지시서에 적지 않는다. 필요한 변수명과 주입 방법만 (예: `DATABASE_URL` — 로컬 `.env`, CI Secrets)
- 인계 대상: test-engineer(독립 검증) → 오케스트레이터(PR)
- 중간 보고 조건: 계약 변경 필요, 환경 장애, 예상 범위 초과(쓰기 범위 밖 수정 필요), 에러 수정 3회 도달
```

## 10-a. 코드 작성 규칙 (가독성)

**코드는 다음 사람이 처음 읽어도 이해할 수 있게 쓴다 (C6).** 모든 구현 에이전트가 따르고, Codex가 검수 관점으로 확인한다.

| 영역 | 규칙 |
|---|---|
| 이름 | 무엇을 하는지 드러나는 이름을 쓴다 (`data`, `tmp`, `handle` 같은 이름 금지). 불리언은 `is/has/can`으로 시작. 도메인 용어는 기획 문서의 용어와 같게 (예: `PostDraft`, `publishedAt`, `RevalidateEvent`) |
| 함수 | 한 함수는 한 가지 일만 한다. 약 40줄을 넘으면 나눌지 검토한다. 매개변수가 3개를 넘으면 객체로 묶는다 |
| 흐름 | 조건이 깊어지면 **early return**으로 평평하게 만든다 (중첩 3단계 이하). 복잡한 조건식은 이름 있는 변수나 함수로 뺀다 |
| 영리한 코드 금지 | 한 줄로 줄이는 트릭, 과도한 체이닝, 이해하기 어려운 축약보다 풀어 쓴 코드를 택한다 |
| 주석 | **"왜"** 를 쓴다 (코드가 "무엇"을 설명해야 한다). 기획 근거가 있으면 문서 위치를 남긴다 (예: `// 예약 글은 예약 시각 유지: 01_backend_plan §5.1`) |
| 매직 값 | 숫자·문자열 상수는 이름 있는 상수로 (예: `MAX_EXCERPT_LENGTH = 160`) |
| 민감 정보 | 비밀값·접속 정보는 **코드에 하드코딩 금지, `.env`로만 주입**. 설정 모듈 밖에서 `process.env` 직접 접근 금지, 비밀값 기본값 금지, `NEXT_PUBLIC_`에 비밀값 금지 ([개요 §6-b](./00_overview.md#6-b-민감-정보-관리-규칙-필수)) |
| 일관성 | 같은 문제는 프로젝트 안에서 같은 방식으로 푼다. 새 패턴을 들이려면 지시서나 G2에서 합의 |
| 타입 | TypeScript strict, `any` 금지 (불가피하면 이유 주석), 반환 타입이 불분명한 공개 함수는 명시 |
| 파일 | 한 파일은 한 개념. 약 300줄을 넘으면 분리를 검토 |
| 에러 | 에러 코드·메시지는 기획 문서의 이름을 쓴다 (`VERSION_CONFLICT` 등). 삼키는 `catch` 금지 |

**자동 검사**: ESLint 규칙으로 일부를 강제한다 — `complexity`(복잡도 10), `max-depth`(3), `max-params`(3), `no-explicit-any`, 금지 이름(`data`, `tmp`, `foo` 등 — 변수·매개변수·함수·클래스 **선언**만 검사하고, Prisma의 `{ data: ... }`처럼 외부 API가 정한 객체 키는 허용. 2026-11-21 개발자 승인). 경고가 아닌 오류로 설정하되, 정당한 예외는 주석으로 사유를 남기고 끈다. 수치는 M0에서 실제 코드로 시험한 뒤 확정한다.

## 12. 도입 계획

| 단계 | 시점 | 내용 |
|---|---|---|
| P0 | 지금 | 이 문서 작성 → Codex 로컬 검수(수동) → 반영 → 개발자 승인 |
| P1 | M0 첫 작업 (오케스트레이터 + 개발자) | git 저장소·**공개** GitHub 저장소, Secret scanning·Push protection, `main` → `dev` 생성 및 기본 브랜치 변경, 브랜치 보호, 이슈 라벨·템플릿, `.claude/` 개편(§11), `AGENTS.md`, 소유권 훅, PR 템플릿, `scripts/codex-review.sh`. (저장소가 아직 없으므로 이 단계만 `dev` 직접 커밋을 허용하고, 끝나면 브랜치 보호를 켠다) |
| P2 | M0 나머지 (DevOps Agent) | 모노레포·CI 셋업(`ownership-check` 포함). **작은 작업 하나로 전체 흐름(이슈 → `dev`에서 브랜치 → 자체 검사 → Codex 최종 검수 @ SHA → push → CI → head SHA 보고 → 개발자 PR 생성·Merge → 이슈 종료)을 처음 시험**한다. 시험 항목: push 시 CI 실행, 검수 후 코드 커밋 시 재검수 요구, `Closes #n`으로 이슈 자동 종료, 범위 밖 파일 변경 시 CI 실패 |
| P3 | M0 종료 시 | 시험 결과로 이 문서와 스킬 보정 (G2) |
| P4 | M1~ | 정식 운영. 마일스톤마다 report에 "협업 체계 개선점" 항목 기록 |

## 13. 위험과 대응

| 위험 | 대응 |
|---|---|
| 에이전트가 쓰기 범위를 넘음 | PreToolUse 훅 차단 + CI 경고 + Codex 검수 |
| 테스트를 구현에 맞춰 약화 | 테스트 파일 소유권(Test Agent), 구현 에이전트 수정 차단 |
| 공유 계약 충돌 (스키마·OpenAPI) | 계약 우선 원칙, 계약 작업 직렬화, 프론트엔드 API 타입 생성물화 |
| Codex 검수 비용·시간 | 로컬 자체 검사(CI와 같은 검사) 통과 후에만 실행, 기획 변경·작업 단위로만 |
| 검수·에러 수정 무한 반복 | 모든 루프 3회 상한, 초과 시 개발자 승인 (C9) |
| 개발자 계정으로 PR을 만들어 GitHub 승인 리뷰를 쓸 수 없음 | G4를 명시적 지시로 받음 (§5.4-a). 필요 시 에이전트 전용 계정·GitHub App 도입 |
| `dev`만 쌓이고 `main`과 멀어짐 | 배포 결정 시 `dev` → `main` 첫 Merge 절차를 별도 계획 (C7) |
| 검수받은 코드와 Merge되는 코드가 다름 | 모든 확인을 head SHA에 묶고, 개발자가 Merge 전에 PR 최신 커밋 = 보고 SHA를 확인 (C13, C17, §6.5). GitHub 화면 Merge는 SHA를 강제할 수 없으므로 이 확인이 마지막 방어선 |
| 작은 작업에도 전체 역할을 실행해 비용 증가 | 실행 방식 선택(§4.0), 필요한 역할만 실행 |
| 계약 변경 중 영역별 병렬 구현으로 가정 불일치 | 크로스커팅 단계별 진행(§5.3-a), 지시서의 계약 기준 SHA |
| 공개 저장소에 비밀정보 노출 | `.gitignore`, Secret scanning·Push protection, pre-commit 검사, 유출 시 즉시 폐기·교체 (§5.1-a) |
| 개발자 승인 병목 | 동시 구현 3개 제한, 보고는 "결정이 필요한 것만" 요약 |
| 기획 문서와 구현의 괴리 | 임의 가정 금지 → G2, Docs Agent의 변경 이력, Codex의 설계 준수 검수 |
| Claude와 Codex가 같은 실수를 공유 | 사람 판정(G3·G4)을 최종 단계로 유지 |
